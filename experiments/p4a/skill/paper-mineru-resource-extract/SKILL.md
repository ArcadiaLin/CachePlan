# Paper MinerU Resource Extract

Use this skill when you are a Kimi worker launched by `src/extract/layer4/launch_kimi_layer4.py` to process one MinerU/PDF paper. The launch script prepares fixed inputs and base templates before you start. Your job is to read the paper, investigate reusable resources, write semantic judgment JSON, and run the local merge script. The launch script will perform final validation after you exit.

This workflow is modeled after `paper-latex-resource-extract`, but it is stricter: do not manually edit YAML. You construct `agent_judgment.json`; local scripts generate YAML.

## Core Rules

- Run commands from the repository root `/home/lzx/projs/p4a`.
- Use `.venv/bin/python` for every script command.
- Do not launch other agents.
- When invoked by the launcher, do not rerun preparation unless a required prepared file is missing.
- Existing references and citation contexts are fixed inputs named in `<output_dir>/input_bundle.json`.
  In the per-paper pipeline these are usually:
  - `/srv/datasets/p4a/data/processed/cite/2026/acl/per_paper/<paper_id>/verified_or_repaired.jsonl`
  - `/srv/datasets/p4a/data/processed/cite/2026/acl/per_paper/<paper_id>/cite_contexts.jsonl`
- Do not ask the agent to repair references or citation contexts.
- Do not manually write `paper_record.yml`, `resource_records.yml`, or any `.yml/.yaml` file.
- You may manually construct only `agent_judgment.json` and plain-text status output; YAML must be generated by local scripts.
- Local scripts are the source of truth for YAML schemas, enum normalization, resource ids, merge behavior, and validation.

## Work On Prepared Paper

When `agent_prompt.md` invokes this skill, start here:

1. Read `<output_dir>/input_bundle.json`.
2. Read the paper Markdown from `markdown_path`.
3. Use `content_list_path` and `pdf_path` only when Markdown is ambiguous.
4. Read the matching citation context and reference data already named in the bundle.
5. Investigate reusable resources mentioned by the paper:
   - datasets
   - benchmarks
   - code repositories
   - models
   - tools
   - protocols
   - APIs
   - project pages
   - released artifacts
6. Use GitHub MCP for GitHub repositories or GitHub project pages.
7. Use the `hf-readonly` MCP for HuggingFace repositories, datasets, models, Spaces, and paper-mentioned datasets/models that are likely available on HuggingFace.
8. Use `arxiv-mcp` for arXiv metadata and source artifacts when the paper has or may have an arXiv version.
9. For HuggingFace resources whose URL is under `huggingface.co`, set `checked_by: hf-readonly` after successful MCP verification. Use `checked_by: pending_huggingface_mcp` only when the URL is HuggingFace but `hf-readonly` is unavailable or cannot be used. Do not use `pending_huggingface_mcp` for non-HuggingFace resources or resources with no URL.
10. Write `<output_dir>/agent_judgment.json`.
11. Run:

```bash
.venv/bin/python src/extract/layer4/apply_agent_judgment.py --paper-id <paper_id>
```

If the output directory is not under the default Layer4 root, pass:

```bash
--paper-dir <output_dir>
```

12. Optionally run validation:

```bash
.venv/bin/python src/extract/layer4/validate_layer4_outputs.py --paper-id <paper_id>
```

If validation fails, fix `agent_judgment.json`, rerun apply, and validate again. Do not patch YAML by hand.

## Semantic Field Rules

### Paper Type

Use only one of:

```text
survey, empirical, benchmark, dataset, method, theory, position, unknown
```

Do not use `resource`, `demo`, `system_demo`, `system_demonstration`, `tool_demo`, or `proceedings`.

For ACL demo papers:

- Use `method` when the paper introduces a system, framework, tool, dataset construction method, or resource-building workflow.
- Use `dataset` only when the paper's main contribution is a released dataset.
- Use `benchmark` only when the paper's main contribution is a benchmark/evaluation suite.
- Use `unknown` only when the paper is front matter or the contribution type is genuinely unclear.

### Claims

Claims are intentionally lightweight for this pipeline. Do not perform fine-grained rhetorical analysis of every sentence.

- Extract 1-2 claims by summarizing the abstract.
- Prefer claims about what the paper introduces, enables, improves, or demonstrates.
- A claim may be a concise paraphrase, not necessarily a verbatim sentence.
- Do not overfit claims to detailed experiment tables unless the abstract itself makes that result central.
- If the abstract has no clear claim, use an empty list.

Good claim examples:

```json
[
  {
    "text": "MapQaTor is introduced as an extensible open-source framework for reproducible, traceable map-based QA dataset creation."
  },
  {
    "text": "The framework speeds up annotation compared with manual methods and supports development of geospatial reasoning resources."
  }
]
```

### Citation Functions

Use only:

```text
background, method_source, dataset_source, benchmark_source, baseline, tool_source, model_source, claim_support, comparison, contrast, related_work, other, unknown
```

If none of these labels is clearly correct, omit the citation function or use an empty string. Do not invent labels such as `material`, `methodology`, `tool_usage`, `future_work`, or `self_citation`.

## Resource Vocabulary

In this skill, "resource" means a reusable external or paper-introduced artifact. It does not mean every concept mentioned in the paper.

Record resources when they are:

- introduced, released, or substantially extended by the paper;
- used as a dataset, benchmark, model, codebase, tool, API, protocol, or project page;
- evaluated in experiments as a reusable benchmark or artifact;
- necessary to reproduce the paper's main system or resource-building workflow.

For experiment sections, explicitly record named datasets and benchmarks used for evaluation, even if they come from cited work. Examples include `GSM8K`, `AQuA`, `MATH-500`, `MMLU`, `MME-RealWorld`, `HumanEval`, or any named leaderboard/evaluation suite. Use `relation_type: used` when the paper uses the resource as input data or an evaluation target, and `relation_type: evaluated` when the paper evaluates on it as a benchmark.

When a named dataset/model has no URL in the paper but is commonly distributed through HuggingFace, use `hf-readonly` to search or inspect the likely HuggingFace record. If a confident match is found, add the canonical HuggingFace URL, license if visible, and a short card-derived description. If no confident match is found, keep the paper-derived resource with `access_type: unknown`, `status: unknown`, and note that the HuggingFace lookup was inconclusive.

Do not record:

- ordinary metrics, equations, losses, algorithmic concepts, broad research areas, or generic tasks;
- every cited paper;
- generic software dependencies unless the paper specifically uses them as a named resource in the system or evaluation;
- individual commercial services such as Google Maps or Apple Maps unless the paper's resource record needs them as explicit API dependencies.

### Resource Kinds

Use only:

```text
dataset, benchmark, code, model, tool, skill, protocol, resource
```

Kind definitions:

- `dataset`: a reusable data collection or corpus.
- `benchmark`: an evaluation suite, task set, leaderboard, or benchmark dataset used for measuring performance.
- `code`: source code, repository, implementation, package, or executable release. Use this only when the paper gives an explicit code repository, package, executable, or code release URL/name.
- `model`: model checkpoint, model family, hosted model release, or trained model artifact.
- `tool`: usable software system, web app, API-backed application, annotation platform, demo system, or service.
- `protocol`: a reusable procedure, standard, annotation protocol, evaluation protocol, or data collection protocol.
- `skill`: a reusable agent-facing workflow/instruction package released by the paper itself.
- `resource`: use only as a fallback when the artifact is reusable but does not fit any other kind.

Important: the current extraction instruction package `paper-mineru-resource-extract` is a Codex/Kimi workflow skill, not a paper resource. Never record this extraction skill as a resource. Only use resource kind `skill` if the paper itself introduces a reusable agent skill or workflow artifact.

If the paper introduces a named framework/system but no explicit source-code release is visible, prefer `kind: tool` or `kind: resource` with `access_type: unknown` over `kind: code`. A GitHub leaderboard or project page related to the paper is not automatically the system's source code unless the paper identifies it that way.

### HuggingFace Verification

Use `hf-readonly` when:

- the paper or citation context contains a `huggingface.co` URL;
- a resource is clearly a HuggingFace model, dataset, or Space;
- a named benchmark/dataset/model used in experiments may have a canonical HuggingFace card.

Record HuggingFace findings in `agent_judgment.json`:

- `access.url`: canonical HuggingFace URL when confidently identified.
- `access.access_type`: `public` when the MCP confirms public access.
- `access.license`: license from the model/dataset/Space card when visible.
- `availability.status`: `available`, `partial`, `missing`, `broken`, `empty`, or `unknown`.
- `availability.checked_by`: `hf-readonly` after successful MCP inspection; `pending_huggingface_mcp` only for unverified HuggingFace URLs.
- `availability.notes`: concise evidence such as resource type, card summary, downloads/likes if useful, or reason for uncertainty.

Do not replace paper evidence with HuggingFace metadata. HuggingFace metadata verifies access and enriches resource descriptions; the `paper_relation.evidence` field must still quote or summarize the paper section that introduced, used, evaluated, or extended the resource.

### arXiv Metadata and Source Artifacts

Use `arxiv-mcp` when the paper title, abstract, citation metadata, or references suggest an arXiv version may exist.

Required arXiv workflow:

1. Use `search_papers` with the exact paper title first. If needed, retry with a shorter distinctive title phrase and first author.
2. If there is a confident match, record arXiv metadata under `paper_record.source_artifacts.arxiv` in `agent_judgment.json`.
3. Use `download_paper` to try downloading the arXiv HTML or source artifact when the MCP supports it.
4. If `download_paper` cannot fetch HTML, use a shell download command to fetch `https://arxiv.org/html/<arxiv_id>` into `<output_dir>/arxiv/html/<arxiv_id>.html`. Do not manually create HTML content.

```bash
mkdir -p <output_dir>/arxiv/html
curl -x http://127.0.0.1:7899 \
  -L --fail --retry 2 --connect-timeout 20 --max-time 60 \
  -A "Mozilla/5.0 (compatible; p4a-layer4/1.0)" \
  -D <output_dir>/arxiv/html/<arxiv_id>.headers.txt \
  -o <output_dir>/arxiv/html/<arxiv_id>.html \
  https://arxiv.org/html/<arxiv_id>
test -s <output_dir>/arxiv/html/<arxiv_id>.html
```

5. Try downloading LaTeX source with a real shell command, not by manually writing a file. Prefer this pattern:

```bash
mkdir -p <output_dir>/arxiv/src
curl -x http://127.0.0.1:7899 \
  -L --fail --retry 2 --connect-timeout 20 --max-time 60 \
  -A "Mozilla/5.0 (compatible; p4a-layer4/1.0)" \
  -D <output_dir>/arxiv/src/<arxiv_id>.headers.txt \
  -o <output_dir>/arxiv/src/<arxiv_id>.tar.gz \
  https://arxiv.org/src/<arxiv_id>
file <output_dir>/arxiv/src/<arxiv_id>.tar.gz
tar -tzf <output_dir>/arxiv/src/<arxiv_id>.tar.gz | head
```

Direct connections to `arxiv.org` and `huggingface.co` from this host are throttled or blocked: always pass `-x http://127.0.0.1:7899` to shell downloads for these domains. Never use the proxy for local services (`127.0.0.1`, `192.168.163.112`). If the download succeeds but the source is a single gzip file rather than a tar archive, keep the downloaded file and mention the `file` result in notes.
6. After a confident arXiv match, do not leave HTML or TeX source as `status: unfetched`. Attempt the fetch. If `curl` succeeds and the file is non-empty, set `exists: true`, `status: available`, and record the repository-relative path. If the fetch fails, use `status: failed`, `missing`, or `unknown` with the command/error in `notes`. Reserve `unfetched` for cases where no arXiv match was available or a legacy template has not been processed by an agent yet.

Use these fields:

- `paper_record.metadata.arxiv_id`: matched arXiv id without `arXiv:` prefix.
- `paper_record.source_artifacts.arxiv.metadata_status`: `available` when `search_papers` produced a confident match; otherwise `unfetched`, `missing`, `failed`, or `unknown`.
- `paper_record.source_artifacts.arxiv.metadata_checked_by`: `arxiv-mcp` after a metadata lookup.
- `paper_record.source_artifacts.html_downloaded.exists`: `true` only if an HTML file was actually downloaded.
- `paper_record.source_artifacts.html_downloaded.path`: repository-relative path to the downloaded HTML file.
- `paper_record.source_artifacts.tex_source_downloaded.exists`: `true` only if a source archive or extracted source directory was actually downloaded.
- `paper_record.source_artifacts.tex_source_downloaded.path`: repository-relative path to the downloaded source archive or directory.

For ACL Anthology papers, lack of an arXiv match is acceptable. Leave artifact statuses as `unfetched` or `missing` and continue resource extraction from MinerU Markdown.

### Multi-Resource Decisions

A single URL may support multiple resources, but split them only when the paper makes the semantic distinction clear.

Examples:

- A GitHub repository that contains an annotation platform should usually be `code`.
- The running web interface of that platform can be `tool` if the paper presents it as a usable system or live demo.
- A benchmark produced using the platform should be `benchmark` if the paper introduces or evaluates it as a named benchmark.
- A project page is usually evidence/access metadata for code/tool/model/dataset, not a separate resource unless the page itself is the released artifact.

For MapQaTor-like papers:

- Record the implementation repository as `code` when GitHub code is released.
- Record the web annotation platform as `tool` only if it is important as a live usable system distinct from the repository.
- Record MapEval-like artifacts as `benchmark` when the paper says "we introduce" or uses them as a named benchmark.
- If a named benchmark/dataset/tool is introduced or substantively used in the experiments, record it even when it is associated with another cited paper. Use the relation type that best matches this paper:
  - `introduced` if this paper claims to introduce or release it;
  - `used` or `evaluated` if this paper primarily uses it for experiments;
  - `cited_only` only when it appears only as background with no experimental or resource role.

## Scripts

The script set lives in `src/extract/layer4/`:

- `prepare_mineru_layer4.py`: prepare one paper directory, base YAML templates, `input_bundle.json`, and a JSON-only Kimi prompt.
- `apply_agent_judgment.py`: merge `agent_judgment.json` into `paper_record.yml`, `resource_records.yml`, `resource_verification_report.json`, and `run_report.json`.
- `validate_layer4_outputs.py`: validate generated YAML/JSON outputs and write `quality_report.json`.
- `launch_kimi_layer4.py`: batch orchestrator that prepares prompts, launches multiple Kimi CLI processes, applies JSON judgment, validates outputs, and writes batch reports.
- `common.py`: shared paths, enums, YAML/JSON helpers, and MinerU Markdown utilities.

## Batch Workflow

Use the launcher for normal batches:

```bash
cd /home/lzx/projs/p4a
.venv/bin/python src/extract/layer4/launch_kimi_layer4.py \
  --references-jsonl /srv/datasets/p4a/data/processed/cite/2026/acl/acl2026_verified_plus_repaired.jsonl \
  --cite-contexts-jsonl /srv/datasets/p4a/data/processed/cite/2026/acl/acl2026_cite_contexts.jsonl \
  --output-root /srv/datasets/p4a/data/processed/layer4/2026/acl \
  --limit 8 \
  --concurrency 4 \
  --timeout 3600
```

The launcher:

1. Selects paper ids from repaired reference JSONL.
2. Skips obvious proceedings/front-matter records by default.
3. Prepares each paper directory.
4. Launches Kimi with a short bootstrap prompt that points to `agent_prompt.md`.
5. Captures Kimi stdout/stderr to `agent.log` and `agent_response.md`.
6. Runs `apply_agent_judgment.py`.
7. Runs `validate_layer4_outputs.py`.
8. If merge or validation fails, writes `agent_repair_prompt.md` with the error details and asks Kimi to repair only `agent_judgment.json`.
9. Retries repair up to `--max-retries` times, default 2.
10. Writes `batch_report.json` and `batch_failures.json`.

## Validation Boundary

If validation fails, fix either:

- the merge script when schema generation is wrong, or
- `agent_judgment.json` when the semantic judgment is wrong.

Do not ask the agent to patch generated YAML directly.
