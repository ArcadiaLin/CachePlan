## C：工具调用评测中的 ToolBench 身份

**来源与状态：** Claude 原候选 C，建议稿，未完成资源身份与案例取证。

**研究需求 / query：** 为工具调用方法寻找相关评测论文和基准，明确任务类型、工具依赖、评分方式及使用条件。

**已有候选与材料：**

- SambaNova 的 ToolBench：[On the Tool Manipulation Capability of Open-source Large Language Models](https://arxiv.org/abs/2305.16504)与 [sambanova/toolbench](https://github.com/sambanova/toolbench)。
- OpenBMB / ToolLLM 的 ToolBench：[OpenBMB/ToolBench](https://github.com/OpenBMB/ToolBench)，原建议涉及 RapidAPI、ToolLLaMA、ToolEval。
- 两个仓库的任务格式、API 依赖与评分脚本，以及 ToolLLM 相关工作中是否说明重名的段落。

**五步路线中的入口：** 从 v1 中使用或讨论工具调用基准的论文找种子；加入同 venue 中任务要求不匹配的候选；沿 ToolBench 名称对应的实际 URL、引用和使用关系向外扩展，保留由同名或通用工具依赖带入的干扰项。

**预期选择转折：** 发现初始候选中的 ToolBench 指向不同实体，核查任务与评分条件后改变对某篇评测论文的适用性判断。

**核查重点：** 资源名称与论文、URL 的对应关系；真实软件工具与 API 任务的区别；是否需要密钥或依赖动态服务。先检查标题、摘要和正文能否消歧，再判断仓库提供了哪些额外信息；ToolLLM 承认撞名的说法需定位原文。

**可复用记录与限度：** 保存同名实体、论文归属、任务格式、依赖和评分条件。主要价值可能是身份消歧与选择；若没有改变论文发现或判断，可作为辅助例子。

## D：代码 Agent 评测中的 SWE-bench 切分与可比性

**来源与状态：** Claude 原候选 D，原建议优先推荐；尚未完成逐项证据核查，推荐不代表已选为主案例。

**研究需求 / query：** 为代码 Agent 寻找可用评测及可比较的相关工作，确认论文数字对应的 benchmark 版本、split 和评测条件。

**已有候选与材料：**

- SWE-bench 原论文及其数据集；原建议给出原测试集 2294 个实例的线索。
- [SWE-bench Verified 发布说明](https://openai.com/index/introducing-swe-bench-verified/)、[Verified 页面](https://www.swebench.com/verified.html)，以及待定位版本的 dataset card、leaderboard；原建议涉及 2024-08-13 发布、500 个实例和 68.3% 筛除比例。
- [The SWE-Bench Illusion](https://arxiv.org/abs/2506.12286)：原建议提到缺少上下文的任务中约 76% / 53% 等数字，以及污染或记忆的解释。

**五步路线中的入口：** 从 v1 的代码 Agent、软件修复或 SWE-bench 使用论文找种子；同 venue 中加入评测对象或 split 不匹配的困难候选；沿数据版本说明、使用关系和后续核查论文扩展，保留只共享名称但条件不同的候选。

**预期选择转折：** 从“都报告 SWE-bench 分数，可以直接比较”，转向核查版本与条件后重新选择可比较论文；也可能沿 dataset card 或后续引用发现补充研究。

**核查重点：** 原集、筛查样本与最终子集的分母和关系；具体分数测的是标准修复任务还是另行构造的探测任务。核实 Verified 在对应时间点的定义来源，不能把“原论文没有定义后续版本”扩写成“所有论文都无法提供信息”。污染与记忆是后续作者的解释，需保留其任务设定、证据强度和不确定性。

**可复用记录与限度：** 保存 benchmark 版本、切分、实例来源、评测条件和已报告问题。后续论文同样是证据来源，不把全部线索归为论文外工件；当前没有证明直接检索或阅读会必然用错 split。

## E：代码生成评测中的测试充分性与版本差异

**来源与状态：** Claude 原候选 E，建议稿，数字与具体排名变化待回源。

**研究需求 / query：** 为代码生成研究寻找评测和比较对象，判断测试覆盖及 benchmark 版本是否足以支撑直接引用已有结果。

**已有候选与材料：**

- HumanEval 与 [EvalPlus / Is Your Code Generated by ChatGPT Really Correct?](https://arxiv.org/abs/2305.01210)，以及需定位版本的测试套件和结果表。
- 原建议线索包括约 80 倍测试用例、18 处参考实现缺陷、约 11% 的题目，以及 19.3–28.9% 的 pass@k 变化；指标、分母、版本和幅度含义均待核查。
- 原建议还提到 WizardCoder-CodeLlama、Phind-CodeLlama 与 ChatGPT 的排名变化，需确认是否来自同一论文版本、结果快照与评测设置。
- 同族数学评测线索 GSM8K → GSM1k 已归入[案例 M](case-candidates-kimi.md#case-m)，保留为跨领域类比。

**五步路线中的入口：** 从 v1 中使用 HumanEval 或相关代码基准的论文定位种子；加入同 venue、结果不可直接比较的困难候选；沿共享测试集、评测实现和后续引文找到 EvalPlus 等工作，同时保留仅共享代码任务主题的干扰项。

**预期选择转折：** 补充测试或版本证据改变对已有结果可比性的判断，促使研究者选择另一组论文或找到测试充分性研究。

**核查重点：** 基准参考实现问题、生成代码问题和评分变化分别是什么；测试版本与模型版本能否对齐；结论来自论文报告还是实际观察测试工件。不要将测试变化概括成所有原结果均无效。

**可复用记录与限度：** 保存测试派生关系、修订项、结果条件和可比性限制。若关键结论在论文中已充分说明，资源增量需落实到具体版本或样例，不能仅以存在测试仓库作为贡献证据。

## F：通过 flash-linear-attention 发现相关方法论文

**来源与状态：** Claude 原候选 F，原建议认为较贴近发现转折、取证成本较高；未有真实检索对照与本地扩展路径。

**研究需求 / query：** 调研线性注意力与次二次序列建模方法，找到可比较的相关工作及实现关系，而不只收集标题中出现相同关键词的论文。

**已有候选与材料：**

- HGRN、Based、Rebased、DeltaNet、GLA、RWKV-6 等方法线索，需逐项确认对应论文和实现。
- [Linear Transformers Are Secretly Fast Weight Programmers](https://arxiv.org/abs/2102.11174)与 [Parallelizing Linear Transformers with the Delta Rule over Sequence Length](https://arxiv.org/abs/2406.06484)：可核查方法来源、命名与后续并行化关系。
- 原建议中的 DeltaNet 于 2024-05、Log-Linear Attention / MoM 于 2025-08 并入仓库的时间点，作为提交历史核查线索保留。

**五步路线中的入口：** 从 v1 中使用该仓库或关联方法的论文找种子；加入同 venue 中术语相近但不满足方法条件的候选；沿具体实现与论文映射、引用向外扩展，并保留仅共用基础库的干扰项。一个大仓库内共存不自动表示方法相同。

**预期选择转折：** 从本地种子使用的实现入口发现初始检索没有返回的方法论文，再通过方法与实现证据确定它为何值得阅读。

**核查重点：** README 是否逐项链接论文、实现位于哪个 commit 和文件；方法继承关系是否有原文或代码支持。记录初始检索、合理改写与常规引文追踪的结果；标题缺词不能证明论文无法被检索。维护活动也不能直接等同于研究价值。

**可复用记录与限度：** 保存“论文—方法—实现”映射、方法间关系及版本。能否形成发现转折取决于真实过程；若普通检索同样直接命中，仍可保留关联组织的价值，但应收窄叙事。

## G：方法描述与实现的一致性——Post-LN / Pre-LN

**来源与状态：** Claude 原候选 G，原建议仅作辅助；尚未核查对应时期的官方实现。

**研究需求 / query：** 为 Transformer 训练设置寻找相关研究，判断层归一化位置、warmup 与稳定性结论能否适用于当前实现。

**已有候选与材料：**

- Transformer 原论文、tensor2tensor 实现与 [On Layer Normalization in the Transformer Architecture](https://arxiv.org/abs/2002.04745)。
- 原建议称论文的 Post-LN 描述与某版官方实现的 Pre-LN 不一致，并关联到 warmup 与训练稳定性；需核实版本和适用条件。
- 同类补充：Ferrari Dacrema 等的推荐系统复现研究及 [RecSys2019_DeepLearning_Evaluation](https://github.com/MaurizioFD/RecSys2019_DeepLearning_Evaluation)。原建议“18 篇中 7 篇可复现、其中 6 篇被简单方法击败”的数字待原文核查。

**五步路线中的入口：** 从 v1 中涉及 Transformer 训练或归一化设置的论文找种子；加入同 venue、设置不同的困难候选；沿实现与后续分析引用扩展，保留共享架构但不回答当前问题的候选。推荐系统例子作为同类线索，不强行接到同一扩展链上。

**预期选择转折：** 实现设置差异改变某篇结论的适用性，或引出专门解释差异的论文。若只影响复现操作，则保留为理解层面的补充案例。

**核查重点：** 官方实现的具体 commit、配置与默认值；原论文和后续论文的实验条件。不能把某版实现代表所有时期，也不能从个别条件推出“不需要 warmup”的普遍结论。

**可复用记录与限度：** 保存方法设置、论文与实现对应关系、结论适用条件。主要支持理解与复现；只有证明它改变了论文发现或选择，才承担本实验的主叙事。
