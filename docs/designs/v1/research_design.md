# 研究设计：面向 CS 研究工作负载的知识数据中间件

更新：2026-09-29。当前定位已明确；下文的工作负载、技术性质与评测方案为候选，具体范围和协议仍需讨论。

本文研究面向外部研究 Agent 的知识数据中间件：持久化保存阅读论文及相关活动形成的知识、解释、语义关系和依据，并提供明确的查询、组合与维护能力。论文的主要评价对象是中间件对研究工作负载的支持，包括可表达的操作、结果正确性、执行与交互成本，以及持续积累时的维护行为。

以人类研究者与 Agent 在特定 CS 任务和研究过程中的共同数据需求为起点，选择有代表性的访问与更新行为。不尝试穷举所有研究行为，也不预设一套适用于全部科学研究的 intent 分类。研究设计按以下关系推进：

**具体研究场景 → 查询与更新工作负载 → 数据模型与算子语义 → 执行机制 → 中间件比较与应用验证。**

场景说明需求从何而来；工作负载明确系统必须处理什么；数据模型和算子共同决定如何表示与操作；评测检查这些设计是否带来可观察的收益。后续任务的完成情况是应用证据，但不能单独说明收益来自中间件。

相关设计见 [数据模型](graph_model.md)、[候选检索算子](operator.md) 与 [算子设计及 Agent 职责边界](../open-questions/2026-09-29-operator-design-and-agent-boundary.md)。

## 1. 问题场景与解决思路

### 1.1 研究场景

以一个具体研究任务为例：**利用有限的领域标注数据，改善通用 embedding model 在专业文献检索中的表现，提出一种适配方法并完成实验验证。**

这是提炼需求的候选场景，尚未确定为评测任务。首先关注其中反复发生的材料定位、记录组合、依据追溯与知识更新，再决定初始工作负载覆盖哪些步骤。

Agent 需要理解任务与数据、形成研究假设、实现方法、设计实验，并根据结果不断调整方案。在这个过程中，论文经验库可以提供辅助：过去阅读时已经理解的方法机制、辨认出的适用条件、整理过的实验依据，以及跨论文比较形成的认识，都可以在当前任务需要时被重新调用。

Agent 将这些经验与当前材料和新实验结合，判断哪些可以沿用、哪些需要重新验证，并继续阅读尚未掌握的内容。

### 1.2 研究 intent 与经验复用

下面保留推进任务时产生的六类 intent，作为工作负载的需求来源。同一 intent 可能多次出现，也可能同时需要几类经验；表格不构成完整的研究行为分类，也不将形成假设、判断可比性或解释实验结果列为中间件内部功能。表中的已有经验均为示意，假设已保存相应条件、关系和原文依据，用来说明它们如何帮助当前研究。

| 研究 intent | 可复用的以往论文经验（示例） | Agent 如何利用这些经验 | 对当前研究任务的帮助 |
| --- | --- | --- | --- |
| **寻找研究切入点。** 我想弄清领域适配中哪些因素值得研究，并提出一个具体、可验证的假设。 | 过去阅读几篇论文时，已经整理出它们分别如何处理训练文本、查询分布和负样本，并把各自声称的收益与消融实验联系起来；还记下了某些实验同时改变多个因素，因而无法单独解释收益来源。 | 复用这份跨论文理解，结合当前数据中的现象，提出例如“固定标注量与训练文本，只改变负样本构造是否有收益”的候选假设。对已有经验没有覆盖的机制和条件，再补充阅读。 | 可以从已经辨认出的机制、分歧和证据缺口继续思考，将宽泛的“提升领域效果”收敛为能开展实验的问题。 |
| **选择和改进方法。** 我想知道哪些已有方案适合当前数据与资源条件，哪些部分能够借鉴或组合。 | 以前已经理解某个“少样本”方案虽然使用较少人工标注，却依赖大量领域语料和教师模型生成数据；另一个方案的训练要求较低，但实验只覆盖了有限的查询类型。这些前提分别连接到方法描述、资源和具体实验。 | 将已知前提与手头的语料、标注、算力和查询类型对照，筛选可采用的组件，明确需要修改的部分，并把尚未验证的迁移条件列为实验假设。 | 提前识别方案的实际代价和适用边界，减少因遗漏论文前提而走到实现阶段才发现不合适的情况。 |
| **设计有解释力的评测。** 我想检验改进是否来自所提出的方法，并判断它在哪些任务和条件下有效。 | 过去对几篇论文的比较已经发现：它们虽使用同名 benchmark，却采用不同的数据切分、训练样本量或候选文档集合；某篇报告的最终结果还包含重排序。资源使用记录与实验条件保存了这些区别，以及各指标实际衡量的内容。 | 复用已有的评测口径对照，选择与专业文献检索需求相符的数据和指标，统一基线条件，将 embedding 本身的效果与后续处理分开考察，再围绕研究假设安排消融实验。 | 避免把设置差异当成方法收益，使实验能够回答当前研究问题，也能解释与已有结果之间的差别。 |
| **把方案落实为实验。** 我想尽快准备一个可信的起点，弄清需要哪些模型、代码、数据和配置。 | 以往阅读已经厘清论文方法对应哪个实现、实验使用哪个模型版本、数据经过什么处理；关键的 pooling、归一化或训练配置分散在正文与附录中，已有记录将它们与资源入口和原文位置关联起来。 | 沿用这些资源对应关系和配置线索准备基线，在执行前核实版本与当前可获得性；对已有记录缺少的步骤，再查原文、仓库或通过试运行确认。 | 减少重新寻找材料和重建论文实现细节的工作，帮助当前实验从与论文描述相符的配置开始。 |
| **解释结果并调整假设。** 我想理解为什么部分查询改善、部分却退步，以及论文中的收益为什么没有在我的设置中出现。 | 过去阅读时，已经记下某项实验中更难的负样本伴随效果下降，作者提出了潜在假负例的解释；另一项工作讨论了相关性标注不完整的局限。这些现象、作者解释和实验依据被分别保留，并建立了可供比较的联系。 | 将这些经验作为排查线索，检查当前负样本及标注情况，提出相互竞争的解释，再通过样本分析和补充实验判断。若条件不同，也据此回查其他可能原因。 | 为异常结果提供有依据的候选解释和下一步实验方向；已有经验帮助提出诊断问题，当前原因仍由新证据确认。 |
| **形成结论并说明贡献。** 我想说清楚这次研究增加了什么认识，哪些结论成立，以及与已有工作的关系。 | 过去已经区分某个方法的核心机制与后续变体，梳理过哪些主张被实验支持、哪些被其他工作限定；相关贡献、方法、主张及其依据之间的联系仍可回看。 | 将当前方法和实验发现放回这些已有联系中比较，识别直接沿用、实质改动与新增证据，补充核查尚未覆盖的相关工作，再组织贡献、局限和 related work。 | 可以延续已有的研究理解来定位新结果，给出具体的比较依据，并让论文中的主张与实际证据相称。 |

### 1.3 外部 Agent 与中间件的职责

“论文理解”在本项目中指外部 Agent 阅读材料、结合任务形成的解释与判断。中间件管理这些内容，并按明确规则操作已有数据；不在算子内部调用 LLM 判断身份、生成命题关系或形成研究结论。

| 工作 | 外部 Agent | 中间件 |
| --- | --- | --- |
| 形成与积累知识 | 阅读、抽取、解释，确定对象身份与关系，提交依据 | 查找候选，接收显式记录与变更，检查结构和引用约束 |
| 利用已有知识 | 分解需求、选择操作、阅读结果，判断条件与适用性 | 执行查询、匹配与组合，返回记录、关系角色、条件描述和来源 |
| 核查与修订 | 判断原文或检查结果支持什么，决定修订内容 | 提供材料，保存明确的核验记录和修订，按约定维护引用与历史 |

例如，系统可以取回已记录的质疑关系，但不据两段自然语言自动判定矛盾；可以并列返回实验条件，但不自动断言两个实验可比。`note` 保存简短提醒，需要证据和修订依据的判断仍由独立知识记录承载。现有候选检索原型中的 embedding 编码放在系统内部还是外部，仍是待明确的实现边界。

## 2. 从研究过程提炼工作负载

### 2.1 候选查询与更新类型

以下操作需求由第 1 节的场景提炼，尚未决定全部纳入 benchmark。每一行是一个工作负载族，可以包含多个组合步骤，不要求对应一个独立工具。后续还应使用具体任务记录和真实材料检查这些需求，避免只挑选当前 schema 容易完成的查询。

| 编号与工作负载 | 输入或触发条件 | 所需结果或状态变化 | 关键边界 |
| --- | --- | --- | --- |
| **W1 对象与说法的候选定位** | 方法、资源等的称呼，或一句命题／问题；可附类型和范围 | 排序候选、稳定引用、类型、定义及召回依据，供后续确认与访问 | 候选相关不等于身份一致或命题等价；词匹配与向量检索的质量单独评价 |
| **W2 研究记录的关联与组合** | 已确认的方法、任务或资源 ID，以及明确的关系、角色和范围 | 相关实验及其被测对象、资源角色、指标、条件描述与来源；可按共同对象组织多篇论文的记录 | 共享资源不表示实验条件相同；不能由论文级关系推断某项实验的资源角色 |
| **W3 命题与问题的关联访问** | 已确认的共同命题或研究问题 ID | 表达该命题或回应该问题的具体主张、来源、已有立场及支持／限定／质疑关系 | 表达同一命题与回应同一问题使用不同关系；不在查询时产生新的语义判断 |
| **W4 来源与依据追溯** | 节点或关系引用、追溯范围及材料读取范围 | 已记录的依据路径、原文位置及按需读取的内容 | 返回依据联系不等于完成核验；来源未记录、材料不可用和结果被截断需要分别说明 |
| **W5 历史记录与核验发现访问** | 资源或主张引用，以及明确的时间、版本或检查类型条件 | 匹配的使用记录或 Observation，保留检查时间、目标版本和证据 | 一次检查的结果不自动代表当前状态；Observation 不要求属于某篇论文 |
| **W6 显式知识写入与修订** | Agent 提交的新记录、关联、修订内容及依据 | 约束检查结果、明确的状态变化，以及按约定保留的变更记录 | 系统执行指定决定；修订、撤回或删除对引用与历史的影响仍需设计 |

W1–W6 是候选需求，不表示当前系统已经完整支持。当前文档已有 `find_entities` 与 `find_statements` 的候选检索设计；组合访问、更新契约和形式化保证仍需收敛。操作名称与实现状态以对应设计和代码为准。

### 2.2 一个工作负载实例需要说明什么

每个实例至少需要明确以下内容，才能用于推导接口与进行比较：

- **任务来源与数据状态**：来自哪项研究步骤；可用论文、已有知识、材料版本和当前快照是什么。
- **输入与范围**：输入自然语言、已确认 ID 还是显式变更；允许访问什么数据，哪些判断已经由外部给定。
- **预期结果或更新后状态**：应返回哪些记录及对应关系，必须保留哪些角色与依据；写入后哪些引用与历史仍应有效。
- **结果语义**：重复、排序、分页、截断和缺失如何解释。库中未记录不等于现实中不存在，候选未召回也不等于对象不存在。
- **独立判定依据与预算**：如何建立参考结果，如何核对内容与原文，以及时间、调用、上下文和构建成本的计量范围。

这些约定应先于实验实现。自然语言 intent 可以保留为入口，但中间件执行的操作和可检查结果需要另外写清楚。

### 2.3 示例：取得方法比较所需的实验记录

外部研究问题是：“方法 M1 与 M2 在 benchmark B 上报告的结果能否比较？”其中一个中间件工作负载可以具体化为：

1. 给定已经确认的 M1、M2、B 的 ID，按明确的实验关系与资源角色查找记录，例如被测方法角色为 `target`、资源使用角色为 `evaluation_data`。
2. 按实验 ID 组织结果，返回关联的方法、资源、指标、任务、条件描述、论文来源与必要的关系属性；缺失信息按约定标明。
3. 按返回的来源引用读取设置或结果材料。Agent 阅读后判断可比性，并决定是否继续访问。

中间件这一部分的正确性可以通过匹配记录、角色、来源及内容完整性检查。若数据切分只写在 description 中，系统返回原描述；不能默默把它当成已有结构化筛选字段。两个实验连接同一 Resource，也不足以确定某条 ResourceRecord 就对应其中某个实验。

这个实例尚不要求 Agent 完成整项研究，也不预设最终可比。它首先检验系统能否准确、完整且以合理成本提供判断所需的数据。

## 3. 由工作负载推导数据模型与算子

### 3.1 需要保留哪些区别

当前 [数据模型](graph_model.md) 是已有设计起点。后续应以工作负载检查它的必要性与缺口，而不是把每个现有节点都预先视为最终需求。

| 工作负载中的需要 | 对表示的要求 | 对操作的要求 |
| --- | --- | --- |
| 跨论文定位并连接同一对象 | 稳定身份、类型、名称与定义，保留版本和消歧线索 | 候选查找与按确认 ID 访问分开；组合时保留对象引用 |
| 区分共同命题与不同来源的说法 | ClaimConcept 与 Claim 分别保存；Issue 组织对同一问题的回应 | 沿明确关系取得具体主张和来源，不用命题归一化覆盖原记录 |
| 组合实验及资源使用信息 | 保留实验、论文局部记录、资源角色和条件描述 | 返回关联记录及关系属性，保持各实验的对应关系 |
| 核查依据并区分作者报告与第一手发现 | 原文锚点、来源关系，以及带时间和目标版本的 Observation | 支持有范围的追溯与材料读取，区分支持关系与核验结果 |
| 积累新材料并修订已有记录 | 明确更新对象、引用与来源；修订历史的表示仍待定 | 定义写入前提、状态变化、失败行为和约束保持方式 |

Entity、Statement 与来源绑定记录的分组解释身份和来源作用，并不强制得到 `findE / findS / findA` 三个算子。比如 Claim 的内容适合陈述检索，其来源记录仍保持独立。各节点可以具有不同字段；共同接口需要统一的是访问语义与结果契约。

### 3.2 算子应具有怎样的技术定义

对选定的操作，需明确输入与输出类型、读取或修改的对象、执行规则、组合方式及结果范围。中间结果可以是节点引用、关系绑定表、来源引用或变更集；具体表示尚未选定，但应能继续参与访问与组合，并保留必要的身份、角色和依据。

接口可以采用通用操作、模型相关视图或显式查询表达式，详见 [算子设计讨论](../open-questions/2026-09-29-operator-design-and-agent-boundary.md)。同一类需求可以由多个操作实现，也不要求每个逻辑操作都独立暴露成 Agent 工具。

技术化的重点是：逻辑操作有明确含义，组合和更新有约束，后端执行能实现这些约定。节点数量、算子数量或接口名称本身不构成贡献。

### 3.3 逻辑表示与后端执行

当前实现基础是属性图与 Cypher。可以将外部 Agent 看作需求解释与规划前端：它把用户需求转成明确操作；系统检查输入与组合，再按规则映射为 Cypher、索引调用或其他执行代码。这是职责与设计方向，不表示已有完整编译器，也不要求立即实现新查询语言。

需要考虑的候选技术性质包括：

- **表示保真**：逻辑模型编码为属性图后，身份、来源、角色与必要属性仍可恢复。
- **查询语义保持**：在同一数据快照和约定的结果语义下，翻译执行的结果与逻辑操作的定义一致。
- **更新约束保持**：满足前置条件的更新完成后，仍满足已定义的类型、引用及其他完整性约束；失败与变更记录的行为需要明确。

例如，对于选定的精确查询范围，可以考虑以下正确性目标：

$$
\operatorname{decode}\bigl(\operatorname{execute}(\operatorname{compile}(q),\operatorname{encode}(D))\bigr)
= \operatorname{eval}(q,D).
$$

其中 D 为逻辑数据状态，q 为合法的查询计划；encode/decode 表示数据与结果的映射，compile 表示后端翻译。这个目标需先规定集合或多重集、顺序、缺失值等语义。近似检索的召回和排序另行定义与评价，不直接套用精确查询保证。

不要求模型或算子与后端一一对应：一个算子可以展开为多步，多个算子也可以合并执行。计划执行正确与 Agent 是否正确理解用户意图分别评价；二者都不能代替对所存知识真实性与证据支持的核查。

即使可以翻译到底层，这层抽象仍需证明实际价值。候选问题包括：能否减少路径和角色使用错误，保留必要来源，降低交互与执行成本，或更可靠地维护已有知识。具体研究机制及其收益尚待确定。

## 4. 以中间件为中心的评测设计

### 4.1 研究问题与候选观察量

下面列出评价维度，后续根据初始工作负载选择具体指标，不预设每项都成为独立实验。

| 研究问题 | 应检查的内容 | 候选观察量 |
| --- | --- | --- |
| **RQ1 工作负载支持** | 哪些查询与更新能表达和执行，支持需要哪些附加步骤 | 分工作负载的支持范围、组合需求、额外代码与外部判断需求 |
| **RQ2 正确性与信息保持** | 精确操作是否符合定义，候选查找是否有效，结果是否保留角色、条件与来源 | 参考结果一致性、必要信息遗漏与错误关联、候选检索质量、更新约束违规 |
| **RQ3 执行与交互效率** | 在可比结果质量下，数据访问和 Agent 使用需要多少成本 | 执行延迟、后端访问量、工具轮次、结果体积与 Agent token 成本；随数据量、查询复杂度和返回规模的变化 |
| **RQ4 积累与维护** | 新材料、修订或核验记录进入后，状态和引用如何变化；已有积累是否减少重复工作 | 更新正确性与开销、历史可追溯性；构建与索引成本在多轮使用中的累计和摊销 |
| **RQ5 应用支持** | 固定外部 Agent 后，中间件是否改善信息取得与任务推进 | 完成率、依据与条件遗漏、总成本及案例；作为系统收益的应用证据 |

“正确性”需要区分两个对象：一是执行相对既定数据状态是否正确，二是数据内容与关系是否受到材料支持。可以用受控快照和独立参考结果检查前者，用独立标注或材料核查检查后者。schema 合法、锚点可解析和答案流畅，都不能替代语义质量评价。

### 4.2 比较对象与实验边界

候选对照包括通用文档／检索式记忆、通用图数据库及查询接口、相关学术知识中间件。具体系统、版本与适配方式尚未选定。比较时应说明各系统实际可用的接口和材料，避免将“需要组合或额外实现”直接写成“无法支持”。

| 比较层次 | 控制条件 | 主要回答的问题 |
| --- | --- | --- |
| **执行机制比较** | 使用相同逻辑数据与查询语义；以人工核对的查询或参考实现为对照 | 翻译与执行是否正确，增加多少开销，有何执行收益；合理编写的直接 Cypher 查询是重要对照候选 |
| **Agent 访问比较** | 固定外部 Agent、任务和可用知识，声明提示与工具适配方式及预算 | 不同接口是否改变计划成功率、信息遗漏、调用轮次和使用成本 |
| **构建与使用的整体比较** | 固定原始材料、任务序列与可比资源预算，分别记录各阶段配置和成本 | 表示、抽取与维护的投入是否在后续使用中得到回报；不能把所有差异归因于算子 |

系统能力表可以区分原生支持、组合支持、需要额外实现或外部判断，以及在声明范围内不支持／尚未验证。每个判定应附具体查询、接口或执行证据。能力覆盖还需结合结果质量和成本评价，不能只按勾选数量得出优劣。

AgenticScholar 可参考其“典型查询—系统设计—能力与成本评价”的组织方式，参见 [原文](../../references/papers/2026-AgenticScholar-reread/paper.txt) §2、§6。其内部 LLM 操作与本项目的职责边界不同，比较时应显式说明。

### 4.3 保留长期积累的评价，同时分开成本来源

初始构建、后续更新和查询使用的成本应分别报告；若主张长期复用收益，需要给出多轮任务或数据演化中的累计成本，明确首次构建何时开始被摊销。只报告查询阶段较少的 token，不能说明整体更经济。

涉及演化时，应固定先前积累、后来可用的新材料和后续查询的顺序，避免未来信息提前进入旧快照。原始论文、Agent 整理的知识、已记录的语义判断和第一手核验发现需要保持区别。

原来的 C1–C6 继续作为需求线索，但按中间件可承担的职责重新解释：

| 原能力 | 当前评价重点 |
| --- | --- |
| **C1 Recall / Retrieval** | 候选检索质量与按引用准确读取记录 |
| **C2 Cross-memory Composition** | 跨记录连接与组合是否保留身份、关系角色和来源 |
| **C3 Context & Condition Awareness** | 是否提供必要条件并保持所属记录；可比性判断由外部 Agent 完成 |
| **C4 Memory Evolution** | 明确修订的执行、引用维护与历史访问；是否改变科学结论由外部判断 |
| **C5 Evidence & Epistemic Awareness** | 来源、已有支持关系、核验记录及缺失状态是否正确呈现；是否拒答由外部 Agent 决定 |
| **C6 Experience Reuse** | 已有记录在后续访问中的可用性和复用成本，再检查对任务的帮助 |

## 5. 当前待收敛的问题与下一步

当前确定的是研究侧重和职责边界。具体工作负载、算子体系、形式化范围、基线与指标仍未定，也尚不能从接口或模型本身推断研究贡献。

建议下一步先完成一个可审阅的工作负载样例：选定一个 CS 研究步骤，列出输入、已有数据、必要结果、缺失和更新情形；用通用查询与候选算子分别表达，检查模型缺口与接口差异。样例讨论后，再决定初始 benchmark 的范围和实验实现。

仍需明确：哪些条件值得结构化、Agent 自己形成的跨论文判断如何归属、修订与历史如何表示、embedding 编码放在哪里，以及哪项数据管理机制构成主要研究问题。后续工作按需求选择，不要求同时解决全部问题。
