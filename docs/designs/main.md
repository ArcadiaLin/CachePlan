# 总体设计

日期：2026-09-18。状态：框架草案，各章内容待填。

本文档记录研究设计方案本身：什么值得表示、如何表示、关系如何保持宽松、如何维护、如何验证。
动机与叙事不在此展开，见 `paper/introduction.zh.md` 与 `docs/discussions/`。

## 核心问题

> **How can we build a paper-knowledge database for agents that organizes and
> manages reading-derived understanding and its complex semantic relationships,
> supporting continual knowledge accumulation and querying, composition, and
> reuse in subsequent research tasks?**

## 范围

本轮只在计算机领域验证，不追求跨领域通用。经济学等其他领域仅作为扩展性讨论出现，
不进入首轮的 schema 设计、实现与评测。

## 1. 设计目标与边界

### 已定：不承担文献发现（2026-09-18）

系统不从全网发现未知论文。论文进入库的前提是用户已经决定阅读它。

讨论稿中的 A1 相应改写为**条件化的关联发现**：给定一个研究需求或一篇新论文，在已读语料
中找出在实验条件、方法假设或评测口径上可比或冲突的工作，并给出可核查的理由。它与全文检索
的区别在于，这类问题需要先把条件抽取出来才能提出，不是文本相似度可以回答的。

接受的代价：评测中不含"发现新论文"类任务，不宣称提升文献调研覆盖率；评测语料限定为已读
集合，任务设计需保证库内确实存在答案。

### 已定：知识面向共享，而非个人复用（2026-09-18）

库的目标形态是可被他人及其 Agent 通过 MCP / skill 消费的资源，而不是某个研究者的私人
记忆。共享比复用多出三条要求：记录必须自解释（读者没有作者的上下文）、可核查（读者不必
信任作者）、有归属（谁在什么条件下观察到的）。

由此得到准入判据：

> **一条观察要进入库，必须带齐足以让第三方重新核查它的条件。标不出核查条件的，不进库。**

排除的例子：个人研究决策（"我上次为什么放弃了 X"）、无条件的整体评价（"这个仓库跑不起来"、
"这篇论文方法不行"）。收录的例子：`commit abc123` + torch 2.1 + A100 40G 下运行报 OOM；
论文报告 LongBench 42.1，使用作者代码在 seed 0–4 上复现得到 39.8±0.6。

需要注意的分寸：剥离个人叙事不等于剥离实验条件。"我在做长上下文实验时试了 vLLM，发现它
不行"应当去掉叙事框架，但结果不是"vLLM 不行"——那已不可核查——而是"vLLM 0.4.2 开启
prefix caching 后，在 >32K 输入下吞吐低于关闭时（A100 40G，实测）"。条件正是使一条观察
可被他人使用的部分。

该判据使第 6 节的定位与版本从附加字段变为准入前提：没有 locator 和版本的观察不可核查，
因而不进库。

### 已定：系统必须能陈述自己的覆盖边界（2026-09-18）

由于库只包含已读语料，任何聚合型回答都必须附带其计算范围，例如"在已读的 N 篇论文中出现过
M 个 benchmark，其中 K 个与你的评测口径匹配；本回答不覆盖未读工作"。不能陈述边界的答案，
与不知道边界的答案，对研究者同样危险。这一要求约束第 7 节：查询结果不只是记录集合，还需
携带该结果是在什么范围上算出的。

### 已定：研究 intent 的接受范围（2026-09-18）

| 研究 intent | 是否接受 | 依据 | 讨论备注 |
| --- | --- | --- | --- |
| 这两篇论文的结果能否直接比较 | 接受 | 需要实验条件对齐判断 | 最能体现"不可简单合并"的约束。条件不同的结果即使数值可比也不应合并，系统需要保留差异而不是消解它 |
| 某方法能否用于当前场景 | 接受 | 适用条件、依赖资源与复现观察 | 依赖的观察须满足准入判据；论文声称的适用范围与实际复现结果分别记录 |
| 撰写 related work 一类的综合 | 接受 | 跨论文综合，需携带支持边界 | 支持边界价值最直接的场景。主要失败模式是过度断言——把论文的设计描述写成已验证结论 |
| 哪些 benchmark 适合某评测任务 | 有条件接受 | 限库内出现过的 benchmark，且必须附覆盖声明 | 表面是发现、实质是关联：需要先抽出每个 benchmark 的任务形态与评测口径才能提问，全文检索答不了。但库内答案必然不完整，缺覆盖声明时不完整清单会被当作完整清单使用 |
| 某篇论文是否可靠 | 改写后接受 | 不给可靠性判断；结合库中已有的客观观察，分层给出作者声称、仓库实际内容、复现结果 | 对应 `references/papers/2026-AutoSci/evidence_map.md` 中 C 类（论文主张）与 I 类（本地静态观察）分开记录的做法。判断留给人与 Agent，系统只负责把不同强度的证据摆开 |
| 某领域最近有什么新进展 | 不接受 | 库外且时间敏感 | 覆盖面劣势是结构性的，设计无法弥补 |
| 复现某篇论文 | 不接受 | 属于执行；但复现过程产生的客观观察需要能够回写 | 执行本身由外部 Agent 与既有工具完成。回写路径与写入门槛见下一小节 |
| 个人研究历程类问题 | 不接受 | 主观且不可核查，见上文准入判据 | 单主体、不可核查、依赖作者上下文，共享的三条要求都不满足。注意剥离个人叙事时要保留实验条件，不要剥成无条件评价 |

### 已定：开放写入，门槛是可核查性而非质量（2026-09-18）

接口与数据模型按开放写入设计：任何接入的 Agent 都可以写，每条记录携带归属（谁、在什么
条件下观察到）。系统不判断记录内容是否正确，只强制结构上的可核查性。

这两件事必须分开，否则范围会失控：

| | 含义 | 是否由本系统负责 |
| --- | --- | --- |
| 质量 | 这条记录说得对不对 | 否。判断内容正确性会退化为逐条抽取优化，属于信息抽取的问题 |
| 可核查性 | 这条记录能否被第三方重新核对 | 是。属于结构性质，可确定性检查，成本有限 |

由此确定研究立场：

> 我们不解决"如何让 Agent 抽取得更准"，而解决"如何组织知识，使错误可被发现、定位并
> 追溯到来源"。

这与数据管理的一般立场一致：数据库不保证数据在业务上正确，它保证约束被满足、来源可追溯、
错误可定位。消费方据归属自行决定信任哪些来源，系统提供归属而不提供信任判断。

范围声明：开放写入是设计能力，不是首轮的评测主张。首轮评测仍使用受控流程构建的库，否则
"谁往里写"会成为无法控制的自由变量。论文中需要写明这一区分。

### 已定：成功标准与失败条件（2026-09-18）

由于不以抽取质量为目标，成功标准落在信息量、可核查性与边界陈述三处，均需可证伪：

1. **信息量**：在相同 token 预算下，本表示对一组预先定义的研究问题的可答率，高于全文
   检索与纯元数据两类基线。压缩率单独不成立，须与可答率配对陈述为"用原文 X% 的 token
   保留了 Y% 的可答问题"。
2. **可核查性**：库中记录可追溯回原始来源并重新核对的比例；以及来源更新后，系统能否正确
   标出哪些记录的定位已失效。
3. **覆盖边界**：聚合型回答能否正确陈述自身的计算范围。该项为二值。

对应的失败条件：

> 若结构化表示在同等 token 预算下的可答率不优于把原文切块直接放入上下文，则该设计失败，
> 无论其表示多完整、组织多自洽。

## 4. 宽松的 schema

- 核心必填字段是哪些，可以少到什么程度？
- 扩展怎么表达：自由属性、类型继承、还是允许后定义的类型？
- 宽松到什么程度仍能保证可查询和可校验？宽松带来的不确定性由谁承担？

## 5. 宽松的关联

- 关系需要多强的类型化？没有预定义类型的关联如何表示、如何被使用？
- 关系自身的属性——证据、成立条件、强度、判断归属——放在哪里？
- 新关系类型出现后，既有记录与既有查询如何处理？

## 6. 证据、定位与版本

- locator 如何统一指向异质来源：正文、表格、图、附录、代码文件、仓库状态？
- 来源版本如何记录？版本更新后如何判定原定位是否仍然有效？
- 论文声称、仓库实际内容、本地执行观察、复现结论如何分级，且不互相顶替？

## 7. 查询与使用

- Agent 实际需要问出哪些问题？先列具体查询，作为表示设计的需求来源。
- 查询结果如何携带支持边界，使下游不会把设计描述当作已验证结论？
- 访问接口的形态：MCP tools，还是更薄的读写原语？

## 8. 维护与失效

- 来源更新后（论文新版本、代码变更、复现推翻原主张），哪些记录受影响？
- 文档被直接编辑后，图侧如何重新对应？无法对应时处于什么状态？
- 维护是写入时触发还是按需触发？未同步状态如何对查询可见？

## 9. 验证方案

- 语料：计算机领域的哪些论文，多少篇，依据什么标准选取？
- 任务：哪些下游任务能够检验这个库的价值？
- 基线：与什么比较，在什么等价条件下比较？
- 指标：抽取正确性、关系正确性、证据支持、下游任务质量、构建与维护成本；
  是否加入过度断言率一类的指标待定。
