# 总体设计

日期：2026-09-18。状态：框架草案，各章内容待填。

本文档记录研究设计方案本身：什么值得表示、如何表示、关系如何保持宽松、如何维护、如何验证。
动机与叙事不在此展开，见 `paper/introduction.zh.md` 与 `docs/discussions/`。

## 核心问题

> **How can we build a paper-knowledge database for agents that organizes and
> manages reading-derived understanding and its complex semantic relationships,
> supporting continual knowledge accumulation and querying, composition, and
> reuse in subsequent research tasks?**

## 范围

本轮只在计算机领域验证，不追求跨领域通用。经济学等其他领域仅作为扩展性讨论出现，
不进入首轮的 schema 设计、实现与评测。

以下为本文档的章节框架。每节列出该节需要回答的问题，答案待讨论后填入。

## 1. 设计目标与边界

### 已定：不承担文献发现（2026-09-18）

系统不从全网发现未知论文。论文进入库的前提是用户已经决定阅读它。

讨论稿中的 A1 相应改写为**条件化的关联发现**：给定一个研究需求或一篇新论文，在已读语料
中找出在实验条件、方法假设或评测口径上可比或冲突的工作，并给出可核查的理由。它与全文检索
的区别在于，这类问题需要先把条件抽取出来才能提出，不是文本相似度可以回答的。

接受的代价：评测中不含"发现新论文"类任务，不宣称提升文献调研覆盖率；评测语料限定为已读
集合，任务设计需保证库内确实存在答案。

### 已定：知识面向共享，而非个人复用（2026-09-18）

库的目标形态是可被他人及其 Agent 通过 MCP / skill 消费的资源，而不是某个研究者的私人
记忆。共享比复用多出三条要求：记录必须自解释（读者没有作者的上下文）、可核查（读者不必
信任作者）、有归属（谁在什么条件下观察到的）。

由此得到准入判据：

> **一条观察要进入库，必须带齐足以让第三方重新核查它的条件。标不出核查条件的，不进库。**

排除的例子：个人研究决策（"我上次为什么放弃了 X"）、无条件的整体评价（"这个仓库跑不起来"、
"这篇论文方法不行"）。收录的例子：`commit abc123` + torch 2.1 + A100 40G 下运行报 OOM；
论文报告 LongBench 42.1，使用作者代码在 seed 0–4 上复现得到 39.8±0.6。

需要注意的分寸：剥离个人叙事不等于剥离实验条件。"我在做长上下文实验时试了 vLLM，发现它
不行"应当去掉叙事框架，但结果不是"vLLM 不行"——那已不可核查——而是"vLLM 0.4.2 开启
prefix caching 后，在 >32K 输入下吞吐低于关闭时（A100 40G，实测）"。条件正是使一条观察
可被他人使用的部分。

该判据使第 6 节的定位与版本从附加字段变为准入前提：没有 locator 和版本的观察不可核查，
因而不进库。

### 已定：系统必须能陈述自己的覆盖边界（2026-09-18）

由于库只包含已读语料，任何聚合型查询的结果都必须附带其计算范围，例如"在已读的 N 篇论文中
出现过 M 个 benchmark，其中 K 个与你的评测口径匹配；本回答不覆盖未读工作"。不能陈述边界的答案，
与不知道边界的答案，对研究者同样危险。这一要求约束第 7 节：查询结果不只是记录集合，还需
携带该结果是在什么范围上算出的。至于消费方是否把这句范围声明写进最终回答，是消费方的事，
库只负责让它可得。

### 已定：研究 intent 的接受范围（2026-09-18）

| 研究 intent | 是否接受 | 依据 | 讨论备注 |
| --- | --- | --- | --- |
| 这两篇论文的结果能否直接比较 | 接受 | 需要实验条件对齐判断 | 最能体现"不可简单合并"的约束。条件不同的结果即使数值可比也不应合并，系统需要保留差异而不是消解它 |
| 某方法能否用于当前场景 | 接受 | 适用条件、依赖资源与复现观察 | 依赖的观察须满足准入判据；论文声称的适用范围与实际复现结果分别记录 |
| 撰写 related work 一类的综合 | 接受 | 跨论文综合，需携带支持边界 | 支持边界价值最直接的场景。主要失败模式是过度断言——把论文的设计描述写成已验证结论 |
| 哪些 benchmark 适合某评测任务 | 有条件接受 | 限库内出现过的 benchmark，且必须附覆盖声明 | 表面是发现、实质是关联：需要先抽出每个 benchmark 的任务形态与评测口径才能提问，全文检索答不了。但库内答案必然不完整，缺覆盖声明时不完整清单会被当作完整清单使用 |
| 某篇论文是否可靠 | 改写后接受 | 不给可靠性判断；结合库中已有的客观观察，分层给出作者声称、仓库实际内容、复现结果 | 对应 `references/papers/2026-AutoSci/evidence_map.md` 中 C 类（论文主张）与 I 类（本地静态观察）分开记录的做法。判断留给人与 Agent，系统只负责把不同强度的证据摆开 |
| 某领域最近有什么新进展 | 不接受 | 库外且时间敏感 | 覆盖面劣势是结构性的，设计无法弥补 |
| 复现某篇论文 | 不接受 | 属于执行；但复现过程产生的客观观察需要能够回写 | 执行本身由外部 Agent 与既有工具完成。回写路径与写入门槛见下一小节 |
| 个人研究历程类问题 | 不接受 | 主观且不可核查，见上文准入判据 | 单主体、不可核查、依赖作者上下文，共享的三条要求都不满足。注意剥离个人叙事时要保留实验条件，不要剥成无条件评价 |

### 已定：开放写入，门槛是可核查性而非质量（2026-09-18）

接口与数据模型按开放写入设计：任何接入的 Agent 都可以写，每条记录携带归属（谁、在什么
条件下观察到）。系统不判断记录内容是否正确，只强制结构上的可核查性。

这两件事必须分开，否则范围会失控：

| | 含义 | 是否由本系统负责 |
| --- | --- | --- |
| 质量 | 这条记录说得对不对 | 否。判断内容正确性会退化为逐条抽取优化，属于信息抽取的问题 |
| 可核查性 | 这条记录能否被第三方重新核对 | 是。属于结构性质，可确定性检查，成本有限 |

由此确定研究立场：

> 我们不解决"如何让 Agent 抽取得更准"，而解决"如何组织知识，使错误可被发现、定位并
> 追溯到来源"。

这与数据管理的一般立场一致：数据库不保证数据在业务上正确，它保证约束被满足、来源可追溯、
错误可定位。消费方据归属自行决定信任哪些来源，系统提供归属而不提供信任判断。

范围声明：开放写入是设计能力，不是首轮的评测主张。首轮评测仍使用受控流程构建的库，否则
"谁往里写"会成为无法控制的自由变量。论文中需要写明这一区分。

### 已定：成功标准与失败条件（2026-09-18）

由于不以抽取质量为目标，成功标准落在信息量、可核查性与边界陈述三处，均需可证伪：

1. **信息量**：在相同 token 预算下，本表示对一组预先定义的研究问题的可答率，高于全文
   检索与纯元数据两类基线。压缩率单独不成立，须与可答率配对陈述为"用原文 X% 的 token
   保留了 Y% 的可答问题"。
2. **可核查性**：库中记录可追溯回原始来源并重新核对的比例；以及来源更新后，系统能否正确
   标出哪些记录的定位已失效。
3. **覆盖边界**：聚合型查询的结果能否正确携带自身的计算范围。该项为二值。

对应的失败条件：

> 若结构化表示在同等 token 预算下的可答率不优于把原文切块直接放入上下文，则该设计失败，
> 无论其表示多完整、组织多自洽。

### 已定：库提供信息，不提供判定（2026-09-20）

两条一体的原则，约束其余各节：

1. **Q1–Q7 是设计探针，不是输出契约。** 它们的作用是倒推"库里必须存在什么结构"，不是规定
   Agent 拿到结构后干什么。Agent 有自己的权限去获取更多信息、自己决定说什么。库不做判定，
   库只负责让判定**有可能被做出来**。
2. **库的职责是把信息充分提供出去，由 Agent 自行理解和使用。** 既不在查询时算出结论，也不
   把结论封装进工具直接返回。

因此本文档中凡写成"系统判定 X"、"算子输出 Y"、"输出可比 / 不可比"一类的表述，均按本条修订：
探针表中的"输出"一列应读作*该探针要求库至少能提供什么*，不是接口签名，更不是对 Agent 行为
的规定。

这与既有条款同构：Q5 只把三层证据摆开、不给可靠性判断；本节"只管可核查性、不判断内容对错"
是同一立场在写入侧的表述。

需要注意本条**不**取消什么：库仍必须让结论**可被算出**。键值化的条件、`evidence_tier`、三元
时间、覆盖范围都是为此存在的数据。"不做判定"指不替 Agent 下结论，不指把判定所需的结构一并
省掉——省掉了，Agent 就只能回去读原文，库也就不存在了。

### 已定：数据库机制的取用纪律（2026-09-19）

目标不是提出新机制，而是把数据库视角在本设定下用完整。相应地，论文的声称形状是：

> 不声称机制新，而声称：当派生数据由 LLM 从自然语言抽出、源头在系统之外、变更以整体
> 重写而非 delta 的形式发生时——**变更可以被检测；保留来源快照后，引用跨度级的失效可以
> 被定位；但重锚定失败、跨度外的语义依赖、以及新增内容导致的失效不能**。我们给出在该
> 设定下的组织方式（含把抽取的哪些部分约束到可确定重算、哪些不可能）与失效判定，给出
> 这条定位能力的边界并测量它，并用 Q1–Q7 证明该组织支撑实际查询。

三条经典前提在本设定下的实际状态（不是简单的"不成立"，而是部分可恢复，边界即设计内容）：

| 经典前提 | 本设定下的状态 |
| --- | --- |
| 派生函数确定，重算即得同一结果 | **部分可恢复**。收紧输出空间（枚举、固定字段集、分类而非自由生成）后，`hardware`、`metric`、`evidence_tier` 等字段可确定重算；claim 的 `statement`、方法的 `assumption` 等自由文本不可；**"一篇论文里究竟有几条 claim"这一抽取数量本身也不可**。这条线画在哪里，属于设计内容 |
| 基表可查、可监听，变更以 delta 到达 | **检测可恢复，定位部分可恢复**。对来源做内容 hash 可检测变更；保留来源快照后可 diff，从而逐条判断"该记录引用的跨度是否变动"。不可恢复的是上述三类 |
| 存在事务与一致性点 | **不可恢复**。跨外部源的一组观察不对应外部世界的任何真实时刻（10:00 查仓库、10:05 查权重，作者可能 10:02 撤了仓库）。后果：依赖多来源的结论，其"截至时间"不是单值，而是各来源观察时间中最旧者——这是第 6 节三元时间的由来 |

"完备"是可信度，不是新意；把它当卖点会被读成 engineering 而非 research contribution。因此
取用纪律为：

> **每引入一个数据库机制，必须能指名它服务第 7 节 Q1–Q7 中的哪一条查询，或本节三条成功
> 标准中的哪一条。指不出的，是装饰。**

装饰的代价不是浪费而是稀释：多一个讲不出用途的模块，全文可信度降一档。按此纪律得到的清单：

| 数据库机制 | 在本设定下它解决什么问题 | 落点 | 服务于 |
| --- | --- | --- | --- |
| schema 与完整性约束 | 开放写入下如何挡住无法核查的记录，同时不去判断内容对错 | 准入判据（可核查、可寻址）+ 写入时 form check | 开放写入；标准 2 |
| 视图 / 物化视图与刷新 | 人读的笔记与机器查的记录如何不各存一份、不互相漂移 | 文档是记录的视图（第 3 节）；刷新产出新观察而非直接改值 | 标准 1；Q7 |
| provenance / lineage | 一条结论出问题时，如何定位到谁、依据哪个来源、在什么条件下写入 | 归属字段、`evidence_tier`、locator 链 | Q5；开放写入 |
| 时态数据（valid time / transaction time） | 观察何时做出、来源是哪个版本、记录何时写入——三者混同则无法判定陈旧 | 记录分别携带三个时间 | Q7；标准 2 |
| 数据集成：schema mapping、entity resolution | 不同论文对同一 benchmark、硬件、设定的命名不同，不对齐则无法比较 | setting 键值化与跨论文实体对齐 | Q1；Q4；Q6 |
| 查询处理 | 冲突关系不预先标注，条件就必须能作为选择与连接的谓词被使用，而非只能整段阅读 | setting 谓词化（第 4 节） | Q1；Q6 |
| 不完备信息语义 | "未查到"、"确认不存在"、"该属性不适用"必须区分，否则下游把缺失当否定 | 多态取值 + 聚合结果的覆盖声明 | Q7；标准 3 |
| 数据质量的边界 | 明确哪部分正确性不由系统负责，否则范围无限 | 只做归属与可核查，不做内容正确性 | 本节已定 |

显式排除（写明比默认不提更能说明想清楚了）：

- **事务与并发控制**：开放写入的难点是归属与可核查，不是并发。指不出对应查询。
- **基于代价的查询优化与索引结构**：本轮语料规模下无可测差异。指不出对应标准。

表中八行机制与上述两项排除，均于 2026-09-19 确认。

## 2. 什么样的论文理解值得进入 schema

### 已定：准入判据只有两条，不含"增量"（2026-09-19）

1. **可核查**：带齐足以让第三方重新核对它的条件与定位（第 1 节已定）。
2. **可寻址**：每条记录必须挂在一个可被他人指名的对象上（论文、方法、benchmark、
   资源、实验配置），不接受游离的散段。

两条都是结构性质，可确定性检查，与第 1 节"只管可核查性、不判断内容质量"的立场同构。

**为什么不把"相对模型已有知识的增量"作为门槛。** 一是判不准："模型是否已经知道这件事"
随模型版本、提示与采样漂移，把一个不稳定量放在准入口，库的内容就随模型变化。二是代价
不对称：多存一条冗余记录的成本是 token，漏存一条的成本是一条边永远不存在，而缺边是
**不可见的失败**——查询时"没有这个关联"与"确实无关"无法区分。三是它已被结果指标管住：
第 1 节的成功标准是同等 token 预算下可答率更高，冗余过多该指标自己会掉。用结果指标约束
冗余，比用准入判据约束更可靠。

**为什么第二条是"可寻址"而不是"可关联"。** 若要求记录必须与库中已有对象建立实际关系才能
写入，写入方过门最省事的办法不是放弃写入，而是挂一条弱关系上去。该门槛因而专门生产语义
站不住的边，而边的正确性正属于第 1 节声明不由本系统负责的"质量"范畴。可寻址只检查记录
有没有主体，不判断语义，不产生这个激励。

孤立记录相应降级为**建库质量指标**：在第 9 节报告孤立率（单篇论文产出的记录中无法与任何
其他对象关联的比例），作为"是否读透、是否该入库"的信号，但不在写入时拦截。

### 已定：L0 保留全文检索兜底，但必须标注层级（2026-09-19）

取消 L1 之后，未进入 L2 的内容只存在于 L0。若 L0 完全不可检索，抽取时漏掉的内容将永久
不可达，系统召回率等于抽取召回率——这与第 1 节"不负责抽取质量"的立场直接冲突。因此 L0
建全文索引作为兜底。

但兜底命中**必须在查询结果中标注来源层级**（结构化记录 / 原文兜底），且评测分别报告
"仅结构化"与"结构化 + 兜底"两组数字。理由有二：

1. 它与第 1 节已定的覆盖边界要求是同一机制——"本条答案来自原文兜底，不是结构化记录"
   本身就是一句范围声明，无需另建设施。
2. 它保住评测的判别力。基线是"原文切块塞进上下文"；若兜底与结构化结果混合报数，系统将
   因**包含**基线而几乎不可能输，第 1 节的失败条件随之变成无法触发的空话。只有"仅结构化"
   能单独报数，该失败条件才是可证伪的。

### 暂定：划界按"是否需要被独立指名"（2026-09-19，待第 7 节确认）

> 一条内容，如果会成为查询的答案、核查的对象或关联的端点，就进 L2；如果它只可能作为
> 另一条已入库记录的解释而出现、永远不会被单独问起，就留在 L0，由兜底检索覆盖。

"会不会被单独问起"在抽取时不可知，落地的近似是**由第 7 节的探针清单倒推**：清单中
任何一类查询需要触及的粒度，即结构化的最小单位。表示由查询需求决定，而非先建表示再找用途。

该依赖关系决定了讨论顺序：**第 7 节先于第 2 节剩余部分收敛**。本条在第 7 节的探针清单
固定后回头确认或修订。

## 3. 知识表示：层次与自然语言的位置

### 已定：两层，不设独立的派生文档层（2026-09-19）

| 层 | 内容 | 产出方 | 可写性 |
| --- | --- | --- | --- |
| **L0 来源副本** | PDF 提取／OCR 后的原文 markdown，带稳定锚点（页、节、表、图）与内容 hash；代码来源则是 commit 快照 | 管线自动生成 | 只读 |
| **L2 结构化记录与边** | 节点、字段、关系，即语义层 | 人或接入的 Agent | 可写 |

L0 不是知识，是**核查的目标**：locator 指向它，来源更新时的失效判定也针对它。

中间不设 L1 派生文档层。**自然语言不被消灭，但必须被寻址**——它以字段值的形式活在记录
内部（claim 的 `statement`、方法的 `assumption`、证据的 `quote`、边上的 `rationale`），
跨论文的综合也是一条以关系为主体的记录，而不是一份自由文档。这与第 2 节的"可寻址"判据
是同一条规则：没有游离的散段。

供人阅读的论文笔记是**视图**，由记录渲染，不是基表。

排除 L1 作基表（文档为主、图为索引）的三条理由：

1. 那正是 AutoSci 的形态（Markdown 实体页 + `edges.jsonl`，图退化为索引），我们与它的
   区别将只剩字段数量。
2. 首轮基线是"把原文切块直接放入上下文"。若系统主体是一份摘要文档，本质上等同于
   "摘要 + 检索摘要"，第 1 节的失败条件很容易触发。
3. 与第 1 节已定的开放写入冲突：该条把写入单元定为"带归属的记录"。若同时允许自由编辑的
   文档层，归属无法落到记录粒度——一段被多方先后改写的散文，说不清哪句是谁的观察、按什么
   条件核查。

**这个选择改变了第 8 节的问题形状**，需记录在案：原本"文档被直接改写后图侧如何重新对应"
（自然语言基表上的视图维护，变更是重写而非 delta）在无 L1 的前提下基本消失，换来唯一真相
源、归属可落到记录、以及首轮评测中"谁往里写"这一自由变量可控。第 8 节剩下的硬问题是
**L0 更新后 L2 中哪些记录的 locator 失效**，它对应第 1 节成功标准的第 2 条，跑不掉。

相应地，第 2 节表中"留在正文"的含义是**不抽取、需要时靠 locator 回 L0 读**，而不是另写
一份文档存着。

## 4. 宽松的 schema

> 落地基线是 `docs/discussions/2026-09-13-layer4-schema-proposal.yml`（Layer4 schema v3
> 提议稿），不是更早的 `p4a-v1-protocol.md`。experiments 一块的具体设计在
> `docs/designs/experiments.md`。

### 已定：不完备信息的取值语义（2026-09-19）

单一 null 不够用。字段缺值必须区分三种情况：

| 取值 | 含义 |
| --- | --- |
| `unchecked` | 没查过 |
| `absent` | 查过，确认不存在 |
| `not_applicable` | 该对象根本没有这个属性 |

服务 Q7 与第 1 节成功标准第 3 条：若三者压成同一个 null，下游会把"没查过"读作"没有"，
在依赖解析中直接给出错误结论（例如把未核查的数据集判为缺失，从而判定方法不可复现）。
聚合型回答的覆盖声明同样依赖这个区分。

**命名待对齐**：Layer4 schema v3 提议稿已实现同一组概念，用的是 `not_checked` /
`not_found` / `not_applicable`。倾向改用 v3 的命名（更接近产物与代码），见
`docs/designs/experiments.md` 的"待确认"。

### 已定：宽松即不假设，结构只加在连接键上（2026-09-20）

第 7 节记下的硬冲突——宽松 schema 与"条件可逐项比对"——**在很大程度上是个假问题**，
不需要用键值化的维度模型去解。

> **跨论文筛选靠的是值，不是把条件拆成受控的维度。** "找用 A100 的工作"是对取值做匹配，
> `8 × A100`、`A100 40G PCIe`、`A100` 都命中；`A100 40G` 与 `A100 80G` 会一起被捞出来，
> 然后由消费方读一眼区分——按第 1 节"库提供信息，不提供判定"，这正是该发生的事。

由此三条，落地见 `docs/designs/experiments.md`：

1. **实验条件就是自由的名值对加定位**，不设受控维度词表，不拆子字段，不做归一。
   预设的维度集必然漏，漏掉的会被塞进最近的名字里，比不受控更糟。
2. **归一的成本只花在会被当作连接键的实体上**：dataset / benchmark / model / metric——
   别的节点要从它们出发连边。`8 × A100` 不需要，图里没有 A100 节点。这与 AgenticScholar
   一致：它归一 Dataset / Metric / Baseline，不归一实验设置本身。
3. **需要精筛时才派生，派生即回写。** 少数维度确实需要范围筛选（`context_length > 32k`），
   原文串做不了；但那是按需的一次派生，作为带归属与观察时间的记录追加，不在建库路径上
   全量铺开。这是第 7 节按需刷新换个地方用，不是新机制。

第 3 条同时是与 AgenticScholar「查询时抽取」的**唯一实质差别**：它每次查询重抽，同一问题
两次可能得到不同数字；我们抽一次写回，第 7 节的 as-of 查询才成立，本节三条成功标准才报得稳。

放弃的设计（同日提出又放弃，记下以免重提）：维度注册表、取值拆受限子字段、evidence 下沉到
子字段。它们买到的是"库自己判出 mem 冲突"，而那件事本就该由 Agent 读一眼完成。

代价：按维度分类的聚合（"N 篇里多少篇报了硬件"）算不出来。接受——覆盖声明落在结构性统计上
（多少篇有条件记录、多少条结果有定位），不需要按维度分类。

### 待定

- 三态命名与 v3 对齐（`unchecked/absent/not_applicable` vs `not_checked/not_found/not_applicable`）。
- 实体归一（dataset / benchmark / model / metric）做到什么程度，由谁做，何时做。
- 按需派生的触发形态：由谁发起、回写到哪、与 Layer4 产物的关系。

## 6. 证据、定位与版本

### 已定：三元时间（2026-09-19）

每条观察分别携带三个时间，不得合并为单一"时间"字段：

| 时间 | 含义 |
| --- | --- |
| 观察时间 | 这次观察是什么时候做出的 |
| 来源版本时间 | 被观察的那个版本本身的时间（论文 v2 的发布日、commit 的提交日） |
| 写入时间 | 这条记录何时进入库 |

三者合一就无法判定陈旧：记录昨天写入，不代表观察是昨天做的，更不代表来源是昨天的版本。
对应时态数据库的 valid time / transaction time 之分。服务 Q7 与成功标准第 2 条；同时是
第 1 节所述"多来源结论的截至时间取各来源观察时间最旧者"的实现前提。

### 待定

- locator 如何统一指向异质来源：正文、表格、图、附录、代码文件、仓库状态？
- 来源版本如何记录？版本更新后如何判定原定位是否仍然有效？
- 论文声称、仓库实际内容、本地执行观察、复现结论如何分级，且不互相顶替？

## 7. 查询与使用

> 讨论顺序说明：本节先于第 2 节剩余部分与第 4–6 节收敛。表示由查询需求倒推，见第 2 节
> "暂定：划界按是否需要被独立指名"。

### 已定：查询探针清单（2026-09-19，2026-09-20 修订定位）

intent 不是查询。"某方法能否用于当前场景"是意图，"输入一组约束、输出候选方法及其适用
条件与复现观察"才是查询；只有后者能倒推出必须存在的结构。下表由第 1 节已接受的 intent
落成查询形状。

按第 1 节"库提供信息，不提供判定"，本表是**设计探针**：第四列读作"该探针要求库至少能提供
什么"，既不是接口签名，也不规定 Agent 拿它做什么。表的真正产物是最后一列。

| # | 探针 | 输入 | 库至少须能提供 | 由此必须结构化的最小单位 |
| --- | --- | --- | --- | --- |
| Q1 | 结果可比性 | 两条 result，或两篇论文 + 一个指标 | 双方条件逐项摆开：均已报告且取值一致的维度、取值冲突的维度、至少一方未报告的维度 | result 为独立节点（metric、value、口径）；experimental_setting 为独立节点，其字段**可逐项比对** |
| Q2 | 方法适用性筛选 | 一组场景约束 | 候选方法 + 各自适用条件 + 已知复现观察 | method 节点带 assumption / requirement；method → 适用范围 claim；method → 复现观察 |
| Q3 | related work 纳入判定 | 一个主题，或一篇正在写的工作的定位描述 | 库内应被纳入的已读工作清单 + 每条的纳入理由（同问题不同方法 / 同方法不同设定 / 被其否证 / 提供基线）+ 各自的支持边界；**库不产出成段文字** | 方法族、问题族等可聚类维度（Q5 不提供）；claim 节点携带支持边界 |
| Q4 | benchmark 选型 | 评测任务描述（任务形态、指标、规模） | 库内 benchmark 清单 + 口径 + 覆盖声明 | benchmark 节点带 task_form / metric / scale；benchmark ← used_by |
| Q5 | 论文可靠性的分层证据 | 一篇论文 | 三层并列：作者声称 / 仓库静态观察 / 复现结果 | 每条记录带 `evidence_tier` 字段 |
| Q6 | 条件化关联发现 | 一个研究需求或一篇新论文 | 在条件上可与之筛选比对的库内工作，及其条件取值与定位 | 同 Q1 的 setting 键值化；条件须能作为谓词跨论文筛选；冲突**不预先标注** |
| Q7 | 研究成果使用依赖解析 | 一个 method / result / paper（"我要复现或使用它"） | 所需资源及其角色（code、dataset、benchmark、model/checkpoint、configuration、environment、external service、version/commit），并区分 required / optional、当前可获得 / 缺失 / 无法确认 | resource 为独立实体；method·result·paper → resource 的使用关系带 `role`；关系本身可携带 version / locator / evidence |

Q5 的 `evidence_tier` 即 `references/papers/2026-AutoSci/evidence_map.md` 中 C 类（论文
主张）与 I 类（本地静态观察）分开记录那套做法的字段化；该做法在本项目读 AutoSci 时已实际
使用过，只是当时手写在表格里。

### 已定：冲突不由写入方预先标注（2026-09-19，2026-09-20 修订表述）

Q6 不依赖写入方事先连出 `contradicts` 边。代价是库必须把实验条件以可在查询时逐项筛选比对
的形式提供出来（判定由消费方做，见第 1 节"库提供信息，不提供判定"）；收益是在第 1 节已定的
开放写入下，标注方案几乎必然漏标——漏标的冲突是不可见的失败，与"确实不冲突"无法区分。这与第 2 节不以"可关联"为硬门槛出于同一考虑：不制造"补一条边就
能过关"的激励。

### 由探针清单导出的硬冲突（2026-09-20 已由第 4 节解决）

Q1 与 Q6 都要求 experimental_setting 的字段**可逐项比对**，即键值化，不能只是一段自然语言。

**理由于 2026-09-20 修订。** 原写的理由是"否则可比性判定退化为让模型读两段话再表态"——按
第 1 节"库提供信息，不提供判定"，该理由作废：Agent 要读两段话是它的自由，库不必拦。真正的
理由是**规模**。给定两篇时，库给出两段原文与定位，Agent 自己读即可；而 Q6 是在全库上做一次
选择，N 篇逐篇读不可行。条件必须能当作**谓词**用于筛选、连接与分组，库才提供了全文检索之外
的东西。

而第 4 节的目标是**宽松的 schema**。不同论文报告的条件维度不同、命名不同、粒度不同（有的
报 `A100`，有的报 `A100 40G PCIe`，有的只报 `single GPU`）。宽松的 schema 与可逐项比对的
条件字段直接冲突。这是本设计中最硬的一处，也是最有可能构成技术贡献的一处。

**解法见第 4 节"宽松即不假设，结构只加在连接键上"**：筛选靠值而非受控维度，条件保持自由的
名值对加定位，归一只做在连接键实体上。落地设计在 `docs/designs/experiments.md`。

### 已定：按需刷新 + 新鲜度界 + as-of 查询（2026-09-19）

刷新外部来源的算子（含 hash 比对、抓取，LLM 本身也可作为算子）**不在读路径上无条件执行**，
而由查询携带的新鲜度要求驱动：

> 查询给出 `max_staleness`。库中观察比该界新 → 直接作答，不触网；比该界旧 → 先刷新再作答。

由此得到三种模式，覆盖不同需要：

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `max_staleness = <界>` | 易变对象（仓库可获得性）界设紧，稳定对象（论文正文）界设松；绝大多数查询不触网 | 日常查询，表现上即"自动更新" |
| `max_staleness = 0` | 无条件刷新 | 主动更新 |
| `as-of <时刻>` | 不刷新，按该时刻的库状态作答 | **评测**：数字可复现 |

**刷新不覆盖旧值，只追加一条新观察**（带观察时间、归属、来源指纹）。这是保留历史、支持
as-of 查询与第 8 节跨版本 diff 的前提。

不采用无条件实时取数的理由：一次 Q7 依赖解析可能触及十个外部资源（延迟、限流、鉴权失败）；
更关键的是评测数字将不可复现，第 1 节的三条成功标准都无法稳定报出。本方案对应的既有机制
为 bounded staleness、deferred view maintenance、freshness-aware query answering 与
as-of / time-travel query，均指得出所服务的查询。

## 8. 维护与失效

### 已定：统一的失效判定，及其能力边界（2026-09-19）

"这个仓库还在吗"与"论文第 42 页那句话还在吗"是同一个问题：**记录所指向的对象，是否仍是
当初观察到的样子**。因此不做两套机制，只做一套：每条记录携带 ① 指向什么 ② 当初该对象的
指纹 ③ 现在指纹是否改变。资源可获得性只是其特例。该机制为本节主线。

保留来源快照后，失效判定可下沉到**引用跨度级**：diff 新旧快照，逐条判断该记录引用的跨度
是否变动；未变动者保持有效，变动者标记待复核。

能力边界（三类失效本机制原理上抓不到，必须写明并测量）：

| 抓不到的情况 | 原因 |
| --- | --- |
| 重锚定失败 | 新版本重新排版，页码、节号、表号移位。内容锚（引用原句）可救一部分，但原句被改写后失效 |
| 跨度外的语义依赖 | 记录引用 p.42 的数字，其成立与否依赖 p.10 的一个定义；该定义改动而 p.42 未动 |
| 新增内容导致的失效 | 新版本增加的实验推翻了已有记录，而所有已存跨度均未变动，diff 原理上不可见 |

对应实验（第 9 节）：在一批真实发生过版本更新的论文与仓库上，测量本机制对真实失效的召回率
与误报率，并按上述三类分别报告未覆盖部分。

由于第 3 节已取消 L1 派生文档层，"文档被直接编辑后图侧如何重新对应"不再是本节问题。
