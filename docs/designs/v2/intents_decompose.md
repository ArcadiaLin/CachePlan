# 代表性 Intent 的分解

> **目的：** 把有来源的研究 intent 展开为数据需求、图查询与外部判断，使不同任务能够逐步检查、相互比较，并据此提炼数据模型与语义算子的设计依据。

本文规定任务分析的共同写法；设计理由与模型、查询相互依赖的处理见 [顶层设计 §4](research_design_v2.md#4-推导方法从任务展开中共同设计模型与算子)。当前尚未确定任务集合与最终算子，下面的记号是分析约定，不是系统 API 或新的查询语言。

## 1. 分解的对象与产物

分解从一个有具体输入、数据状态和结果要求的任务实例开始。Intent 说明目的，来源说明为何选择，操作过程说明怎样取得完成任务所需的数据，以及何处需要 Agent 判断。

```text
有来源的 intent → 具体任务 → 数据变量 + Cypher + Agent 判断
                                      ↓
                            可检查的过程与结果
                                      ↓
                          跨实例的候选模式及表示需求
```

来源可以是论文任务、benchmark 原题、评测规范或研究者的实际需求。每个实例保留链接或材料位置，区分来源直接提出的要求与我们的改写。代表性首先指有外部依据并覆盖不同的信息需求，不预先声称覆盖全部研究活动。

## 2. 统一表达元素

### 2.1 数据：所有步骤使用和产生的变量

| 记号 | 含义 | 必须说明的内容 |
| --- | --- | --- |
| `u` | 用户需求与约束 | 当前要解决什么问题 |
| `G` | 持久化属性图的当前状态 | 本例使用的标签、属性、关系方向和角色 |
| `refs` | 对象或材料引用 | 身份是否已确认，引用指向什么版本或位置 |
| `rows` | 查询返回的记录 | 每行代表什么，字段及关联的含义 |
| `materials` | 读取到的原文等材料 | 来源、位置及读取失败或缺失情况 |
| `decision` | Agent 产生的判断或决定 | 内容、依据、不确定性与后续用途 |

每个实例按需增加变量。标量、列表和记录都可以使用，但必须声明来源与含义。**任务需要的数据与当前已经存储的数据分别写明。** 自然语言描述不能默认为已抽取的字段，候选引用不能默认为已确认身份。

### 2.2 Agent：需要结合需求与证据的判断

```text
decision = Agent(
    goal     = 本步要作出的判断或决定,
    context  = 用户需求与前序结果,
    evidence = 当前可用记录或材料,
    output   = 预期输出的字段及含义
)
```

`Agent` 是外部推理的抽象位置，类似策略选择的占位，不规定模型、提示词或训练方式。它可以解释需求、确认身份、判断可比性、选择后续操作或形成结论；每次调用必须说明具体问题及输出，不能用“完成任务”包住所有未展开步骤。

显式条件下的匹配与筛选写成查询；需要解释条件含义、判断证据是否足够的步骤写成 `Agent`。输出允许“待核查”或“无法判断”，并说明依据。**调用 Agent 只标明判断发生在哪里，不保证判断正确。**

### 2.3 Cypher：明确的图读取与更新

```text
rows = READ(G, Q, params)
(G_next, rows) = WRITE(G, Q, params)
```

`Q` 是另行列出的 Cypher 文本，`params` 显式绑定其中的 `$参数`。`READ` 不改变图；`WRITE` 表示成功执行后的图状态及返回结果，后续使用 `G_next`。它们仅用于区分状态变化，不是候选领域算子。

每个查询块应写清输入参数、返回列和依赖的临时 schema。读取按需使用 `MATCH`、`OPTIONAL MATCH`、`WHERE`、`WITH`、`RETURN`、聚合或子查询；更新按具体需求展开，并说明目标、前提和预期变化。不得用未定义的 `FindMethod`、`CompareResults` 等名称替代查询本体。

结果按照查询本身的语义理解：不默认去重或排序；需要保留缺失关联时明确处理方式。特别是，返回空结果只表明本次查询没有匹配，不能直接推断现实中不存在该对象或现象。

### 2.4 控制流程与外部访问

使用普通赋值、`if/else`、`for`、有停止条件的循环和 `return` 连接各步骤。分支读取已产生的变量；若分支条件本身需要语义判断，先通过 `Agent` 得到明确输出。

原文读取、全文检索或向量检索按需写为 `External(...)`，逐项说明实际操作、输入、输出与缺失行为。它表示需要单独声明的外部能力，不假定属于核心 Cypher，也不能成为隐藏推理的黑箱。

对 Cypher 的变量流和子句组合，参照 [官方语义说明](https://neo4j.com/docs/cypher-manual/25/clauses/clause-composition/)。本阶段使用已有查询语言表达任务，不另建一套查询代数。

## 3. 一个任务实例的固定格式

每个实例使用稳定编号，例如 `T01`，按以下顺序展开。实际任务必须填入具体内容；下表是写作模板，不是已经完成的任务分解。

| 部分 | 必填内容 |
| --- | --- |
| **目的与来源** | 用户口吻的 intent；来源位置、选择理由及改写范围 |
| **输入与结果** | 输入、约束、预期输出或更新效果、完成条件 |
| **数据约定** | 可用材料、初始图状态、临时 schema、已确认与未知信息 |
| **过程** | 数据变量、逐步伪代码、对应的参数化 Cypher；显式标出 Agent 和外部访问 |
| **检查依据** | 如何核对查询结果、更新效果和判断；缺失或失败时返回什么 |
| **模式线索** | 本例要求保留的语义区别、候选操作结构及尚未解决的缺口 |

**过程写到能顺着变量追踪为止：** 每一步的数据从哪里来，产生什么，下一步为什么使用它，都应可见。例子使用临时模型时，必须先给出定义，不能让读者从查询中猜测图结构。

对需要补充材料的任务，写明补充访问的目标、允许范围和停止条件。对更新任务，显式分开“Agent 提交修改决定”和“数据库执行修改”；说明失败时的处理，不默认具备尚未设计的回滚或历史维护机制。

## 4. 如何检查与提炼

每个实例先分别检查三个层次：

| 层次 | 检查问题 |
| --- | --- |
| 任务符合性 | 这组步骤取得的信息是否足以支持用户目的？仍缺什么？ |
| 数据操作正确性 | 查询或更新是否符合已声明的数据约定，保留正确的身份、角色、条件和证据？ |
| 外部判断质量 | 判断是否有据可依，不确定性是否保留？ |

手工审阅、样例执行和独立结果核对是不同验证状态，应据实标记。伪代码写完整不等于已经执行或验证。

比较多个实例后，为候选模式记录：**支持它的任务编号、共同输入与输出、操作结构、参数差异、必须保留的语义，以及适用边界。** 单例可以提出候选，跨实例分析再检验复用与组合价值。

尤其检查同一论文中的方法与实验是否真的对应，条件是否在聚合后丢失，已有判断是否被误写成新结论。若模式只由某种临时 schema 的写法造成，应回到任务需求重新分析。

最终产物是有任务依据的模式与表示需求，供后续共同设计模型和算子。具体实例在约定初始任务范围后逐一补入；本文件不预先把候选 intent 或示意流程认定为 benchmark。
