## 1. 为什么重新打开数据模型问题

此前讨论从候选检索出发，逐渐把节点概括成 Entity、Statement 和 Artifact，并进一步讨论是否应该有 `findE / findS / findA`。随着研究侧重转向数据库中间件，问题变成了：这些分组是否足以成为领域模型的基本抽象，支撑明确、可组合的查询与更新？

用户希望 Agent 操作的是建立在属性图之上的学术知识对象，而不必每次阅读底层 schema 说明、选择关系路径、编写 Cypher。当前设想是：识别模型上符合任务需求的查询与更新模式，将具体值抽象为参数，固定操作结构、领域规则和结果形式，形成算子；再通过合法组合覆盖选定工作负载。

因此，讨论重新回到用户提出的顺序：

> 数据模型固定住了，列出在数据模型上要进行的增删改查，然后再演化算子。

这是一条设计推进思路，但不要求在尝试任何操作之前就冻结所有模型细节。共同访问需求可以帮助归纳类型，具体查询与更新也可以暴露模型缺口；两者需要迭代收敛。

用户转述老师认为 `entity / statement / artifact` 不合理。老师针对分类、具体节点还是整体建模方式的详细理由与例子尚未补充。下文关于分类维度混杂和模型缺口的分析来自本次对话与文档核查，不能当作老师的原话或已确认结论。

## 2. 原三分法的来历与需要修正的说法

以下是此前讨论中的分组，记录它是为了检查问题，不表示继续采用：

| 原分组 | 包含的节点 | 原先采用的依据 |
| --- | --- | --- |
| Entity | Paper、Method、MethodConcept、Task、Resource、Metric | 有名称或标题，通过称呼检索；确认身份后跨论文共同引用 |
| Statement | ClaimConcept、Issue | 用命题或问题文本表达，作为跨论文语义入口 |
| Artifact／论文局部记录 | Contribution、Claim、ResourceRecord、Experiment、Observation | 保留具体来源和条件，不把不同论文或活动的记录直接合并 |

这个分组混合了内容形式、检索方式、身份复用与来源范围。它最初有助于解释候选检索，但还没有被论证为稳定的顶层类型体系。后续提出的新三类并不是给这三类改名：Method、Metric 等对象的归属与 Claim 的表示层次都可能重新安排。

- **Claim 内容上也是陈述。** 它适合陈述检索，同时需要保留论文来源；这两个特征可以同时成立。当前 `find_statements` 已经检索 Claim，查询范围与原三分法并不一一对应。
- **Issue 表达问题。** “回应同一问题”和“表达同一命题”需要保留不同关系语义；这种差异不妨碍 Issue 与 ClaimConcept 共享候选检索接口。共同检索既不能证明它们的一切操作都相同，也不能因为语义不同就否定接口复用。
- **Artifact 的范围不清楚。** Paper 也可以被理解为文献 artifact，论文草稿还用 knowledge artifacts 泛称所管理的知识记录。将该词专用于第三类容易混淆。
- **Observation 并非论文局部记录。** 它来自一次检查、运行或复现，绑定时间、目标版本和证据，不要求隶属于单篇论文。
- **不合并记录不等于不能复用知识。** 具体 Claim、实验和检查记录都可以被后续任务检索与引用；“可复用／不可复用”不足以单独解释其内容类型。

还需修正助手此前过于简单的判断：不能只用“删除顶层分类后，底层还能保存这些记录”来否定分类的技术作用。分类也可以组织共同接口、检索策略和写入管理规则。需要检查的是这些作用能否具体定义并带来收益，而不是要求每种分组首先成为一套排他的本体分类。

## 3. 新的候选理念：研究实体、概念性对象与研究表达

### 3.1 从组织论文到组织研究表达

用户的起点是“将论文组织起来”。新设想进一步关注论文中的实验、贡献陈述、论断和解释，使这些内容能通过共同涉及的实体与思想跨论文连接，并保留各自的来源与上下文。

常见的实体中心建图方式可以描述“论文提出方法、使用数据集、引用另一篇论文”。当前设想强调研究表达的组织与访问，但不能据此声称传统知识图谱只能描述简单实体关系，或不能承载主张、证据和来源。这里的差别首先是领域组织方式与操作重点，尚不是已经成立的新颖性结论。

| 用户提出的类别 | 讨论中的暂定名称 | 举例与直觉 | 候选管理重点 | 对划分理由的质疑 | 对疑问的回答 |
| --- | --- | --- | --- | --- | --- |
| Entity | 研究实体 / Research Entity | Paper、Dataset、CodeRepo、已发布模型或权重；可通过出版、发布和版本记录在系统外指认 | 身份、元数据、版本、访问位置，以及哪些研究表达引用了它 |  |  |
| 尚未命名的抽象对象 | 概念性对象 / Conceptual Object | 方法思想、指标定义、概念、公理、命题，以及可共同讨论的问题 | 定义、含义、语义联系，以及表达对它的采用、讨论或回应 | 这些概念从哪里来？一篇新论文刚出来就有个名称吗？例如“日心说”这个名称，是等一批主张太阳是中心的claim，集合才成了日心说，在此之前可没有一个日心说能够入图 | 我们侧重于对论文中已有知识的聚合，演化是支撑的下游方向之一，例如有了update算子之后，至少能够支撑，我们将一组claim，组建成更加集中的概念 |
| Content | 研究表达 / Research Expression | 实验描述、贡献自述、某来源中的具体论断、分析或解释 | 内容、上下文、提出者、整理过程、来源与证据 |  |  |

这些英文名称由讨论暂定，类的边界与成员尚未选定。尤其是用户提到的 claim，需要进一步区分作为讨论对象的命题与某来源中的具体表达；不能直接把原有 Claim Label 整体搬进第二类。第三类目前以论文内容为主要来源，但“研究表达”的设想允许继续讨论论文之外的活动记录。

用户用 URI 解释第一类对象的外部可定位性。更准确的候选表述是“身份由外部记录锚定”：URI 可以标识资源，也可以标识抽象概念，本身不是物理存在或类别归属的判据。[RDF Primer](https://www.w3.org/TR/rdf11-primer/#section-IRI) 第二类围绕定义与含义组织，也不要求该命题已获共识或被判为真；有争议的命题仍可以作为共同讨论对象。

### 3.2 逻辑模型、访问视图与存储表示

用户明确补充：**三类分组不限制底层跨类关系，也不假设各类内部只有简单结构。** 用户以 Transformer 为例，区分 Hugging Face 的 Transformers 软件框架、Transformer 模型架构，以及某篇论文中的具体记录；这些对象可以分别保存并通过明确关系相连。名称相近不要求合成一个节点。这一补充已经排除了“三个桶会切断关系”或“同名对象无法跨层组织”的攻击。

需要区分三个层次：

| 层次 | 当前理解 |
| --- | --- |
| 领域逻辑模型 | 直接管理三类候选对象及其关系。任何一类都可以成为查询或更新的对象，也可以通过其他对象连接 |
| 面向任务的访问视图 | 可以围绕研究表达，把共同实体或概念作为表达之间的连接依据；也可以直接访问实体版本、概念关系等 |
| 实现与存储 | Neo4j 属性图保存结构、身份和关联，文件系统承载正文、表图等材料；一个逻辑对象不要求等于一个存储节点或文件 |

“逻辑图的节点只有研究表达”是最初的设想。经质疑后，用户认可三类在逻辑上仍相对平行，需求也要求直接操作它们。因此，表达之间的图应作为候选访问视图，不再预设为整个系统唯一的逻辑模型。

在表达视图中，一条关联可以由底层路径得到。例如，两项实验分别把同一数据集用作评测数据，可以形成保留数据集和两侧角色的关联结果。候选结果结构可以是“表达 A、A 的角色、共同对象、B 的角色、表达 B”，但尚未决定统一中间表示。这样的路径连接不自动表示实验可比、论断相同或彼此支持。

用户用汇编与 CPU 操作类比底层图的表达能力。这个类比支持“上层抽象不必与底层节点和边一一对应”；它尚不证明接口已经完备，或底层任意可达路径都有领域意义。后续又明确关系类型应有限、可枚举：底层关联可以丰富，但不能将这种丰富理解为 Agent 可随意发明关系语义。

## 4. 分类如何服务算子与 Agent 接口

### 4.1 用户补充的设计动机

分类有叙事用途，也服务于算子设计。用户当前设想让算子直接作为 Agent tool 暴露；如果每种节点都有不同结构与特殊接口，Agent 就需要理解大量工具、参数与调用方式，难以体现比直接面向 Label 写查询更好的使用体验。

用户希望从类内共同特征出发，统一数据结构和查询机制。ClaimConcept 与 Issue 可以共用文本及向量候选检索，是这一思路的具体来源。因此，“分类只有故事、没有技术作用”这一笼统攻击已经不成立；分类对接口数量、检索流程与使用负担的实际影响，仍需验证。

现有 [find_statements 原型](../../experiments/e08/src/e08/operator/find_statements.py) 对 ClaimConcept、Issue 和 Claim 共用词匹配、向量检索与 RRF 融合，说明访问机制的复用已有代码例子。它还跨越了原来共享命题与来源记录的分组，说明复用接口不必严格限定在某个顶层类别内。这里只记录静态实现事实，不宣称当前检索质量已通过评测，也不据此冻结原接口。

### 4.2 尚待选择的统一程度

| 方案 | 来源与状态 | 需要检查什么 |
| --- | --- | --- |
| 类内对象具有相同数据结构与查询机制 | 用户希望继续深化的方向 | 哪些字段和行为真正共同；是否需要保留子类型的专有语义，是否适合所有类内对象 |
| 共同操作具有一致输入输出与行为，内部允许字段不同 | 助手提出的替代建议，尚未定案 | 能否通过结果投影与内部适配隐藏无关差异，同时让后续操作保持明确含义 |

例如，title、name、text 可以按操作需要映射到共同返回结构，但这只说明可以统一一次访问，不意味着对象身份、所有字段或全部更新规则也已经统一。一次检索使用共同向量流程，也不足以决定所有概念性对象应采用完全相同的检索策略。

需要保留两个区别：**节点类型数量不必等于 tool 数量；逻辑算子与 tool 的封装粒度也需要设计。** 100 种节点并不必然需要 100 个工具，但把差异全部塞进一个有大量特殊分支的工具，也未必降低理解负担。分类、参数化接口与算子组合应共同减少需要解释的特殊规则，不能只追求工具数更少。

### 4.3 预置概念与受控扩展

用户说明，先将部分概念入库，是为了给后续抽取提供对齐入口，避免 Agent 随意生成概念降低图谱质量。这项做法与分类、候选检索配合，应单独记录；本文未核查具体预置内容，也不将“图谱质量已提高”作为已验证结论。

预置哪些对象、依据什么定义、如何处理新概念、谁确认身份和关系、是否保留未对齐候选，仍待明确。预置词汇不能成为把所有新内容强行归入已有概念的理由；候选查找与语义确认继续分工。

### 4.4 从检索性能直觉转向访问语义（2026-09-30）

用户进一步提出：Entity 具有确定的 identifier 和元数据，适合精确定位；概念可以通过 BM25 等方式检索；Content 则承载更开放的文本内容。最初尝试用“Entity → Concept → Content 的精确率递减、召回率递增”，或信息量、信息熵来解释分类。其核心直觉是：**即使三类都使用混合检索，在候选处理和后续操作上仍有不同需求，这些访问需求可以成为分类理由。**

经讨论，用户认可将论证支点调整为“检索目标与匹配成功条件不同”，暂不采用上述性能排序。精确率和召回率需要相对于具体查询及相关结果集合定义，并不是对象类别的固有属性。例如，按已知 DOI 查找论文，可以同时具有很高的精确率与召回率；在指定论文和章节中定位实验记录，也不必低精确率。BM25、向量检索都可以用于三类对象，不能由所用检索算法直接推出分类。

当前认可的候选表述是：

> 三类对象具有不同的访问语义：实体访问侧重身份定位，概念访问侧重语义对齐与关系导航，研究表达访问侧重带来源和上下文的内容定位。它们可以共享混合检索基础设施，但需要不同的候选处理、结果契约与后续操作。

| 候选类别 | 典型访问问题 | 匹配成功的条件 | 混合检索之外需要明确的处理 |
| --- | --- | --- | --- |
| Entity | 我要找的是否就是这个对象或版本？ | 身份及版本符合请求 | 身份键解析、命名空间与版本约束、元数据过滤 |
| Concept／概念性对象 | 哪些已有概念表达了这个含义，或处于指定概念范围内？ | 按请求满足已确认的同义、上下位或其他明确关系；相似候选仍需另行确认 | 定义与规范称呼、候选对齐、按显式规则展开关系 |
| Content／研究表达 | 哪里具体表达或记录了这件事？ | 找到符合条件的表达，并保留其来源和上下文 | 来源定位、表达粒度、条件与角色过滤、证据及内容取回 |

这里的 identifier 指能够用于核对指称对象的身份键，不只是系统分配的 node ID；三类对象都可以有内部 ID。哪些 Entity 具有可用的外部身份键、身份键是否区分版本、缺失时如何处理，仍需明确，不能假定该类别天然都能精确消歧。

概念检索返回语义相近候选，不等于确认两个概念相同。系统可执行已有对齐关系和显式导航规则，新增语义判断仍由外部 Agent 负责。表中的三种访问语义描述各类的主要需求，不是互斥能力：概念也可按 ID 读取，研究表达也可做语义检索，实体也可能需要名称候选检索。它们尚不足以证明恰好三个顶层类别最合适。

信息熵暂不作为分类的理论依据。若以后用它刻画候选消歧的不确定性，需要先定义随机变量、候选空间与概率分布；标识符、概念描述和段落的长度或抽象程度，不能直接推出检索熵的高低。目前也没有测量结果支持三类的固定性能排序。

### 4.5 从访问语义导出操作与组合

这轮讨论把分类的设计理由推进为以下待验证链条：

> 代表性访问需求 → 不同的匹配与上下文要求 → 对象类别及共同操作契约 → 统一接口与关系组合 → 检查工作负载支持及使用成本。

分类希望统一的是类内共同操作契约。例如，不同实体可以使用不同外部身份键，但共享身份查找与引用接口；是否进一步统一全部字段，仍保留 §4.2 中的两种方案。接口是否简化，要检查子类型的特殊参数和规则是否实际减少，不能由三类名称或工具数量直接推出。

跨类关系则使一次定位能够成为下一步操作的明确入口。一个候选查询链是：

```text
定位某个数据集版本
    → 取得使用该版本的实验表达及使用角色
    → 取得这些实验明确支持的主张及限定
    → 返回对应论文和证据位置
```

这条链依赖明确保存的身份、角色、支持关系和来源，以及组合时保留它们之间的对应关系。它不依赖三类检索的性能排序，也不允许从共同使用数据集自动推出实验可比或主张相互支持。这里描述的是对已存关系的查询，不是中间件自行生成科学判断；示例尚不是已实现接口或确定的 benchmark。

**当前进展是形成了由访问语义驱动的分类假设，目标是统一类内操作并支持跨类组合。** 尚待检查：各类共同契约能覆盖哪些具体对象，哪些差异必须保留，访问需求是否支持当前三类边界，以及查询上的共性是否延伸到写入和维护。不能只凭检索分类就认为身份、修订和删除语义已经得到解释。

## 5. 质疑、回应与当前判断

下表对应本轮六项主要攻击及用户逐项回应。判断针对论证是否回答问题，不是对用户或方案作整体否定。

| 助手提出的攻击 | 用户的回应 | 当前判断与仍待完成的部分 |
| --- | --- | --- |
| **1. 三类划分缺少语义约束力，可能只是叙事。** 删除三个顶层类别后，具体节点与关系仍能工作 | 分类用于统一类内结构与检索，减少直接暴露给 Agent 的工具和参数差异；已有共享检索原型，也考虑预置概念 | **回应有效，原攻击范围过大。** 分类可以产生接口与处理机制上的作用，不必先证明没有它就无法存储。尚未证明恰好三类最合适、每类都能完全统一，或工具减少必然降低使用成本 |
| **2. 丰富的关系不能自动确定哪些路径有领域意义。** 例如使用某框架，不足以证明采用它支持的任意架构 | 关系应有限、可枚举，类似语言中的基本操作符；提出关系本身有层级与组合时如何处理的问题 | **方向有效，但尚未完整回答。** 排除了无规则扩展关系的解释；仍需逐项定义关系含义、可用路径及组合条件。枚举关系名不能自动确定上述框架例子的查询结果 |
| **3. 表达作为唯一逻辑节点可能不足以支持直接管理实体与概念。** 底层可表达，不等于上层已提供相应操作 | 认可质疑；三类在逻辑上相对平行，任何一类都可通过其他类关联，需求要求这样 | **已形成修正。** 完整模型管理三类对象，表达中心组织保留为访问视图；不再坚持唯一逻辑节点都是表达 |
| **4. 三分法未解决类内身份与粒度。** 家族、版本、子集及表达修订影响连接含义 | 由数据结构与有限关系表示这些区分，通过层级关系分开家族内部对象 | **回应提供了表示方向，定义仍未闭合。** 关系能承载区别，但还需规定节点指称、身份条件，以及何时新建而非修改。家族成员关系与集合子集关系也需分别定义 |
| **5. 查询视图清楚，不代表更新含义清楚。** 删除一条派生关联可能对应多个不同底层修改 | 数据结构与关系固定后，CRUD 随最终模型冻结而确定 | **如果最终模型包含更新策略，此回应成立；仅冻结字段与关系枚举则不足。** 还要选择引用处理、修订、撤回和历史规则；不能把这些规则视为由静态结构自动推出 |
| **6. 三类对象与跨类关系仍面对成熟方案，尚未建立研究贡献。** 需要同等数据与合理查询封装的比较 | 接受，作为评测和设计理由的备忘 | **保留为未解决的研究问题。** 新方案需要用工作负载支持、正确性和成本说明价值；Agent 接口负担是新增的可评测方向 |

此前已被用户补充排除的攻击，不应继续重复：三类之间不能连边；同名对象不能在不同层次出现；存储图必然只有简单结构。助手也需要撤回“分类若不改变可存储内容，就没有技术作用”的过强判断。

仍然不能作为充分论证的简单说法包括：“每种节点都需要一个工具”“类内字段相同就意味着所有操作相同”“关系有限就意味着组合规则明确”“字段与关系冻结后更新策略自然唯一”“工具数更少就证明 Agent 更容易使用”。它们是需要具体机制和证据补齐的推断，不是已被证明的结论。

一个仍有检验力的例子是：

```text
实验 E ——使用—— 框架 R
框架 R ——实现—— 架构 T
框架 R ——实现—— 架构 U
```

查询“采用 T 的实验”时，不能仅靠这段路径确认 E。模型应保存本次实验实际选择的架构或实现对应，算子按明确关系返回结果；这不要求系统调用 LLM 补猜。有限关系表可以帮助定义这些记录，但表中有“使用”和“实现”两个名字，尚不足以完成定义。

## 6. 有限关系、层级与组合：怎样控制范围

### 6.1 三种不同的问题

用户从体系分类法和组配分类法提出疑问：对象有层级可以通过边表达，关系本身若也有层级，是否会不断产生新的关系，是否必须覆盖从属、参照、交叉、同族等组织方式？讨论中需要先分清：

| 层次 | 示例 | 应定义的内容 |
| --- | --- | --- |
| 对象间的层级或归属 | 数据集 D1 是 D2 的子集，资源 V 属于家族 F | 端点分别表示什么；子集、组成部分、类别实例和家族归属不是同一关系 |
| 关系类型的层级 | “使用评测数据”是“使用资源”的特例 | 查询父关系是否包括子关系；含义是同一对端点上的关系包含 |
| 关系的路径组合 | 两个资源分别属于共同家族 F | 按什么路径与条件连接，返回哪些对应关系和连接依据 |

RDFS 的 [subPropertyOf](https://www.w3.org/TR/rdf-schema/#ch_subpropertyof) 提供了关系类型包含的参考：通过子关系联系的对象，也通过父关系联系。OWL 的 [property chains](https://www.w3.org/TR/owl2-primer/#Property_Chains) 则提供了指定关系链蕴含另一关系的表达参考。两者不是一回事，也不意味着本项目需要采用完整 RDF／OWL 推理系统。

“同族”可以先作为共同家族上的连接查询，不必都物化为基本边。“交叉”也可能是几个查询条件的交集，而不是新的关系类型。某个词究竟表示基本关系、路径结果还是过滤组合，需要由工作负载和语义定义决定。

### 6.2 有限的是基本词汇与规则，不是所有查询表达式

当前可采纳的设计方向是：**为初始范围选择有限、明确的基本关系与组合规则，通过组合表达更多查询。** 不能把“有限、可枚举”扩大为必须预先列出全部合法路径、全部复合概念或所有自然语言需求。

沿用户提出的组配思路，可以分别记录方法、任务、资源等维度，再按需要组合条件；无需给每一种维度组合命名一个新类别或关系。这是讨论中的工程解释，并不宣称三类对象已由某套分类学理论推导出来。

关系类型层级也可以先通过一份有限定义表或查询展开规则实现，无需把每个关系类型都改为存储图中的普通节点。只有被选定工作负载要求的组合才需要进入首版范围；这能暂缓全面的分类与推理系统，但不能省略已支持关系的含义。

候选关系定义应说明名称、端点类型、方向、角色和必要限定，并按需要声明是否支持父关系展开、逆向访问或特定路径组合。没有声明的规则不自动应用；逆向访问也不等于关系对称。有限词汇约束当前 schema 版本，不意味着未来永远不能受控扩展。

### 6.3 直接记录与派生结果要能区分

不能因为关系存在层级，就默认任意关系都可传递。例如 SKOS 区分直接的 `broader` 与可传递的 `broaderTransitive`，一般关联 `related` 也不提供传递推导。[SKOS Semantic Relations](https://www.w3.org/TR/skos-reference/#semantic-relations)

在本系统中，按显式路径得到共同家族、共同资源等结果，可以作为查询结果返回，并保留原始记录与连接依据。是否将它们另存为关系，以及原始记录修订后如何维护，属于独立的更新设计。按规则计算这些结果不意味着系统可以自动推断科学支持、矛盾或可比性。

## 7. 具体模型中仍需解决的缺口

以下问题来自对原有模型的核查。新方案不能因为改了类别名称就视为已经解决；也不要求必须继续使用表中的原 Label 才能解决。

| 问题 | 当前定义与疑问 | 对操作的影响 |
| --- | --- | --- |
| **Agent 自己形成的判断如何归属？** | Claim 被定义为根据一篇论文整理的主张；实验部分又要求把 Agent 的跨论文比较判断写成 Claim。例如“两篇论文的实验不可比”可能是 Agent 综合得出的结论，不能直接归给其中一篇 | 来源查询、写入和修订需要区分原判断的提出者、判断依据与整理过程；不能借用 note 避开归属问题 |
| **Experiment 的粒度是什么？** | “一项实验”可能覆盖整张比较表，也可能只表示一个配置。若同时连接多个方法、数据集和指标，现有边未必表达它们之间的具体对应 | 查询可能只能返回共同出现的对象，无法直接给出准确的“方法—资源—指标—设置”组合；需决定是读取描述，还是进一步明确记录粒度与关联 |
| **共同命题与新概括如何区分？** | ClaimConcept 表示共同命题，但“归纳”容易被理解成从多个局部发现推出更广结论。含义相容也不自动意味着命题相同 | `EXPRESSES` 的建立、修改与拆分需要明确准则；新增适用范围的综合判断不能悄悄当作同义归一化 |
| **身份、版本与修订怎样区分？** | Resource 可表示资源族或具体版本；不同层次的身份约定尚需细化。修改描述可能是在纠正认识，也可能实际上更换了指称对象 | 需要决定何时原地修改、何时新建并关联；修改 Claim 的条件后，已有命题联系与支持关系是否仍适用也要处理 |
| **哪些内容必须可计算？** | 许多实验条件、版本和限定在 description 中，数值保留在原文表图中 | 可以返回材料供 Agent 阅读，但不能直接承诺对尚未结构化的条件精确过滤、连接或聚合；所需结构化程度由工作负载决定 |

还需明确来源路径与关系约束。例如，Claim 与 Paper 的直接归属、经 Contribution 的归属应如何配合，是否允许缺失或多个来源；关系的 description 与 anchor 是否包含操作必须一并返回的限定。来源结构可检查与内容受到证据支持是不同问题。

对第 4 项，用户提出由结构和关系确定粒度是可行的设计方向。下一步需把“一个节点代表什么、哪些变化保持身份、哪些变化新建对象”写进定义，避免只是增加 `SUBSET_OF` 或家族边，却仍无法判断两个引用是否指向同一版本或集合。

## 8. 算子从头设计：由共同操作与模型约定导出

当前讨论认可的方向是领域操作封装：通用图查询语言提供底层表达能力，领域模型和工作负载决定需要暴露哪些操作。这里无需宣称 Cypher 是“最完备”的语言，也不要求我们的操作具有超越底层语言的表达能力。

“把有意义的查询写出来，抽出参数，固定形状，包装成算子”可以作为设计方法，但需进一步明确固定的是哪些领域规则。比如查询问题回应时，Agent 不必自行选择 `RESPONDS_TO` 路径和 stance 所在位置；这些细节可以进入接口定义。具体路径和字段仍取决于重新审视后的模型，不能据此冻结现有关系。

### 8.1 CRUD 需要回答的语义问题

| 操作 | 除底层图操作之外需要定义什么 |
| --- | --- |
| 新建 | 新建的是共享对象、某次表达还是某次活动记录？需要什么来源？重复提交是否产生重复记录？ |
| 查询 | 按身份、内容、来源还是关系访问？返回哪些对应关系？缺失、多值、排序和截断如何解释？ |
| 修改 | 修改属性、修正身份判断与形成新版本如何区分？哪些既有关系或派生索引受到影响？ |
| 删除／撤回 | 是物理删除、撤销判断还是停止作为当前有效记录使用？已有引用与历史怎样处理？ |

这些问题还没有完整答案。不能把对各 Label 的通用 CRUD 换成领域名称，就视为领域操作已经定义充分。同一份静态结构可以选择不同的更新策略，例如删除被引用对象时拒绝操作，或按约定同时处理引用；字段和关系名不会替我们选择策略。

因此，需要共同冻结的是：对象与关系结构、合法状态的约束、已支持操作的状态变化与失败行为。可以先明确有限的更新范围，不要求一次支持任意修改。修订内容时，图内记录、文件内容版本、原文位置与已有引用如何保持对应，也属于操作约定。

对派生的“表达 A 与表达 B 共享问题 Q”关联，不应在没有约定的情况下提供含糊的删除：撤销 A 的关联、撤销 B 的关联、修正 Q 的身份，或仅排除当前视图中的一对结果，会产生不同状态。

### 8.2 包装与组合需要一起考虑

一个参数化查询可以成为独立操作；一组操作要支持组合，还需要明确输入输出类型与对应关系。可选的中间表示包括带类型的对象引用、关系绑定表、保留关联结构的记录集合等，当前没有选定统一形式。

例如“问题 → 回应主张 → 来源 → 实验依据”的组合，需要持续保留哪个来源和实验对应哪条主张。不能把每一步都变成无对应关系的对象列表，再让 Agent 重新猜测。类型匹配也不保证整个计划符合用户意图，任务规划仍由外部 Agent 负责。

需要检查的是：有限的领域操作及其合法组合，能否覆盖选定工作负载，而不是为每个完整问题各写一个专用函数，也不是承诺覆盖所有可能的学术研究查询。底层可以使用一条或多条 Cypher、索引调用及其他代码，逻辑操作不要求与物理实现一一对应。

“无需更多说明文档”在这里理解为：Agent 不必额外阅读内部 schema 和实现细节才能正确调用。领域接口仍需简短且明确的功能、参数、结果和副作用说明。

### 8.3 从头设计不等于按新三类各写一个工具

现有算子清单、名称与分组不作为新接口的骨架。应先明确共同操作、参数、结果和组合，再决定 tool 的封装方式；三类对象不自动推出三个检索工具或三套完全独立的 CRUD。

已有词匹配、向量检索、融合与后端查询代码可以作为实现经验，是否复用由新契约决定。节点属于哪类、操作作用于哪些类型、一次调用返回什么，应分别写清楚。重新设计的目标是减少无关差异和特殊规则，同时保留工作负载需要的语义，不能为了统一而丢失条件、角色或来源。

## 9. 理论目标、既有工作与评测备忘

用户的顾虑还包括：当前模型与算子能否支撑数据库化的技术叙事，是否需要超出目前能力范围的理论工作。讨论阶段应先把可检查的语义写清楚，而不是要求先建立完整代数、编译器或科学论证系统。

需要区分三个层次：表示与操作是否定义明确，后端是否正确实现这些定义，以及这些设计是否实际改善工作负载的支持。可选择有限范围的表示保真、查询语义保持或更新约束保持作为技术目标，但尚未决定证明范围，也不能把这些性质当作已实现的保证。近似检索和所存科学判断的证据支持需要分别评价。

模型的充分性应相对于明确的工作负载判断。能把内容写进 description 不等于能执行所需查询；只有查询样例也不足以说明修改和删除行为合理。另一方面，领域操作封装是否有研究价值，还需比较能力、正确性和成本，不能由名称、数量或公式直接推出。

用户已接受既有方案与研究贡献问题需要保留为备忘。[SKOS](https://www.w3.org/TR/skos-reference/) 提供概念组织机制，[PROV-O](https://www.w3.org/TR/prov-o/) 提供来源、派生与修订表达，[Micropublications](https://arxiv.org/abs/1305.3506) 组织科学主张、证据及跨文献联系。这些参考不等于已实现本项目全部需求，但“分为三类并跨类连接”不能单独作为新颖性结论。

比较对象需要包含同等数据与信息访问条件下、具有合理 schema 和认真编写查询或更新接口的系统。不能只拿裸 Cypher 的使用体验与经过封装的本系统比较，就把所有收益归于新模型。

| 候选评测方向 | 需要检查的内容 |
| --- | --- |
| 工作负载支持与正确性 | 可表达的查询和更新、结果对应关系、条件与来源保留、修订后的约束保持 |
| Agent 接口负担 | 工具选择与参数错误、所需说明和上下文长度、计划构造与执行成功率、交互次数及成本；工具数仅是指标之一 |
| 检索与概念治理 | 候选召回、错误归并和重复记录；预置词汇的对齐收益，以及新概念不能进入或被强行归入的代价 |
| 执行与维护成本 | 查询、构建、更新与持续复用成本，随数据规模变化的行为 |

这些是候选评价维度，尚未确定实验任务、比较协议或实现计划。应区分同一批已存知识上的执行比较与完整构建使用过程，避免把抽取质量、外部 Agent 判断和中间件执行的影响混为一谈。

## 10. 下一轮讨论希望得到什么

先不沿用旧算子清单继续加名字。当前需要把新候选理念变成可以检查的定义，再决定具体类型和接口。

可以先为每类候选对象整理共同操作约定：典型输入、返回结构、候选检索方式、可共用的行为，以及必须保留的子类型差异。用这份约定检查分类是否帮助减少接口负担，再选择“类内完全统一结构”或“统一访问契约、内部允许差异”等方案，不预设其中一个已经获选。

沿 §4.4–4.5 新增的访问语义理由，下一步应具体检查身份定位、概念对齐与导航、带来源的表达定位分别要求什么匹配条件和输出，再用一条跨类查询及一次关联修订检查组合与维护。以实际契约是否共用、对应关系是否保留来检验分类，不以预设的精确率／召回率排序替代论证。

具体对象与关系还应说明：

| 约定 | 要回答的问题 |
| --- | --- |
| 指称与粒度 | 一个节点究竟代表什么？哪些情况应拆成不同记录？ |
| 身份 | 哪些变化仍是同一个对象，哪些意味着新对象或版本？ |
| 来源 | 谁提出内容，依据是什么，谁在何次活动中整理或形成判断？ |
| 关系与组合 | 基本关系有哪些，端点和角色是什么，哪些父关系展开、路径组合或层级访问被允许？ |
| 生命周期 | 新建、修改、关联、撤回或删除时，哪些约束和历史需要保持？ |
| 写入与扩展 | 哪些词汇预置，哪些记录允许直接新增，谁确认新概念及语义关系？ |

可用于检查的情形包括：框架、架构与具体使用记录的对应；不同论文表达同一命题但保留独立依据；Agent 形成新的跨论文判断；一项实验覆盖多种配置；资源发布新版本或身份判断被修正。这些是讨论样例候选，不是已确定的 benchmark 或实施任务。每个例子可同时写一个查询和一次更新，检查三类与关系规则分别承担了什么工作。

工作顺序可以是“共同操作需求与候选模型 → 具体查询及更新 → 暴露缺口 → 修订并冻结初始范围 → 确定算子与 tool 封装”。数据模型大改、算子从头设计的方向已经明确；新的三类边界、字段、关系词汇、更新策略和接口还未定案。本次文档更新记录这些区别，不授权直接启动 schema 迁移、实验实现或全量运行。
