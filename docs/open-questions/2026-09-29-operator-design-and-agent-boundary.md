## 1. 为什么提出这个问题

此前从实体检索与命题检索的区别出发，讨论明确了一个认识：当前数据模型经过有意设计，希望保留长期研究活动需要的对象身份、具体主张、适用条件、实验经验和来源联系。接下来的问题是：**既然数据模型有这些区别，系统应该提供怎样的操作方式，让外部 Agent 能够正确取得、组合和维护这些数据？**

讨论曾提出包含 `resolve_entity`、`relate_statements`、`compare_records`、`assemble_context` 等内容的候选表。随后与 AgenticScholar 的算子库对照，发现两份表的范围和抽象层次并不一致，也暴露出职责边界的问题。

用户明确提出的顾虑是：

> Agent 是在数据管理系统外部的使用者，这个算子不应该有 LLM 参与。

> 什么是算子？输入输出固定就好，还是互相关联？输入输出接得上？

> 要从我们的数据模型出发。

需要保留的主要疑问如下：

| 疑问 | 需要进一步回答的内容 |
| --- | --- |
| 什么才算一个算子？ | 固定参数和返回格式是否足够？是否还应规定操作语义、类型、组合规则与副作用？ |
| “贴合数据模型”具体指什么？ | 是为每类节点设计接口，还是围绕共享身份、论文局部记录、关系角色和依据路径设计访问方式？ |
| 算子之间如何组合？ | 中间结果传递节点、关系、表格还是子图？怎样保留来源与角色，避免依靠 Agent 重新解析文本？ |
| 基础操作与复合操作如何分工？ | 哪些能力由通用遍历、匹配和集合操作完成，哪些值得固定成模型相关视图？ |
| Agent 与系统各承担什么？ | Agent 判断身份、条件和关系；系统执行明确的数据访问与更新。这个边界如何落实到每个接口？ |
| 候选检索中的 embedding 放在哪里？ | 现有原型内部调用 embedding 模型。禁止 LLM 语义操作与禁止一切模型调用的实现边界需要区分并约定。 |
| 算子设计如何进入论文贡献？ | 哪些属于必要工程接口，哪些管理机制值得研究？怎样避免从算子名称或数量反推创新性？ |

## 2. 已明确的职责边界

**外部 Agent 负责理解材料、形成判断和决定下一步；系统按照明确规则保存、访问、组织和更新已有数据。** 数据管理服务不调用 LLM 临场解释任务、判断内容或生成研究结论。算子的含义应由参数、数据模型和执行规则确定。

数据中可以保存 Agent 先前形成的理解与判断。查询这些记录时，系统读取的是已有判断及其依据，不重新完成一次语义推理。

| 工作 | 外部 Agent 的职责 | 数据管理系统的职责 |
| --- | --- | --- |
| 理解新材料 | 阅读、抽取和撰写候选记录，标明依据 | 提供已有材料及定位；接收显式提交的记录 |
| 判断实体身份 | 核对定义、来源、版本，决定复用、新建或暂不确定 | 查找候选，返回定义与关系，执行明确的写入决定 |
| 建立命题联系 | 判断共同命题、共同问题及支持、限定、质疑等关系 | 读取已有联系，保存 Agent 指定的关系及依据 |
| 比较实验 | 阅读条件，判断可比性、适用性及仍未知的内容 | 返回实验、资源角色、指标、描述和原文位置 |
| 核查主张 | 判断指定材料支持了什么、支持到什么程度 | 追溯与读取材料，返回已有支持关系或核验记录 |
| 形成任务上下文 | 决定当前任务需要哪些信息，解释取得的内容 | 按显式路径、字段、筛选条件和预算组织结果 |
| 积累与修订 | 提交新增理解、纠正理由及依据 | 检查结构与引用约束，执行变更并保留相应记录 |

系统可以检查节点类型、关系端点、引用存在性、必填字段及约定的更新规则。原文锚点可解析、关系类型合法，并不能证明内容忠实于原文或判断成立；语义正确性仍需独立评价。

这一边界也适用于看似通用的操作。例如，按已存储的 `resource_id` 分组可以由系统执行；把“语义上相同的方法”自动分组需要先有 Agent 的判断或库中已有的身份联系。按明确数值排序属于数据操作；根据开放指令判断“研究价值”并排序属于 Agent 工作。

### 2.1 对上一版候选表的修正

| 先前候选 | 按当前边界重新定位 |
| --- | --- |
| `find_entities`、`find_statements` | 保留候选检索职责，不承担身份或命题等价判断；模型调用边界见第 7 节 |
| `resolve_entity` | 其中的语义身份判断移到外部 Agent；若以后使用同名接口，必须说明是执行显式身份决定还是产生判断 |
| `relate_statements` | 关系判断移到外部 Agent；系统负责查询或写入已明确指定的关系 |
| `compare_records` | 语义比较由 Agent 完成；系统可提供按显式键连接、按字段并列展示的操作，不自动判定可比性 |
| `trace_evidence` | 保留，按已定义路径取得来源与依据，不等同于验证主张 |
| `assemble_context` | 是否独立成算子待定；可按显式路径、字段、排序和预算组装，不能在内部调用 LLM 理解意图或生成摘要 |
| `apply_delta` | 保留为写入候选，接收明确变更；具体约束、修订单位和记录方式待设计 |

## 3. 怎样借鉴 AgenticScholar

AgenticScholar 的算子表主要面向查询执行计划，包含检索、图导航、语义内容处理、集合处理与生成。其执行层允许 LLM 参与查询分析、抽取、比较、核验和生成；它的 `Search`、`MatrixConstruct` 本身也可以包含多个内部步骤。其知识构建与 taxonomy 更新另有机制，不能从查询算子表未列写入操作推断该系统不维护知识。

这张表可以帮助思考操作如何分类和组合，但不能直接照搬它把语义判断纳入服务内部的职责划分。尤其需要分别检查同名操作的实际执行方式：

- `FindNode`、`Traverse`、`Retrieve` 中的定位、遍历与读取思路可以参考。
- `Extract`、`Summarize`、`Check`、`Verify`、`Generate` 中的 LLM 理解和生成工作，在我们的边界下由外部 Agent 完成。
- `Filter`、`GroupBy`、`Aggregate`、`Rank` 可以采用明确字段与规则实现；名称相同不代表执行语义相同。
- `MatrixConstruct` 不直接成为我们的必需算子。是否需要特定矩阵或视图，应由当前模型和研究意图决定。

参考：[AgenticScholar 原文](../../references/papers/2026-AgenticScholar-reread/paper.txt) §5.1、附录 D；[论文入口](https://arxiv.org/abs/2603.13774v1)。

## 4. “算子”的工作定义与组合问题

暂用如下工作定义：**算子是在指定数据状态上，按照明确规则，将具有约定类型的输入转换为输出的数据操作；写算子同时产生明确的状态变化。** 这是一项设计约定，尚不表示要建立完整查询语言、形式化代数或自研执行引擎。

| 需要定义的内容 | 讨论中的要求 |
| --- | --- |
| 输入与输出类型 | 规定接受哪些对象及返回结构；固定类型不等于固定返回条数 |
| 操作语义 | 说明读取哪些字段、沿哪些关系、如何过滤与组织结果；自然语言检索文本可以作为数据输入，不作为任意执行指令 |
| 组合方式 | 明确哪些输出字段或引用可以进入后续操作；不要求所有算子两两相接，也不要求所有结果类型相同 |
| 结果范围 | 明确方向、深度、可选关系、去重、排序、分页与截断；未返回、未记录和不存在需要区分 |
| 状态与副作用 | 区分读取和写入，说明写入前提、变更内容及返回记录 |
| 物理实现 | 接口职责与使用的索引、查询实现分开描述；近似检索需说明范围，不能承诺逻辑等价或完备召回 |

“输入输出接得上”至少有两个层面：技术上能传递对象，以及语义上不丢失下一步需要的区别。只返回可读文本或节点名称，虽然 Agent 能看懂，却不一定适合继续遍历、连接与追溯。

### 4.1 中间结果的候选表示

| 候选类型 | 内容 | 可继续参与的操作 |
| --- | --- | --- |
| 节点引用及记录集合 | 稳定 ID、类型、所需属性；候选检索另带名次与召回依据 | 按 ID 读取、筛选、遍历、连接 |
| 关系与匹配结果表 | 绑定的节点、关系引用、方向、角色和属性 | 投影、连接、分组、后续路径匹配 |
| 来源引用集合 | 所属材料、锚点及已记录的版本信息；必要时带回溯路径 | 原文读取、定位核查 |
| 原文内容块 | 对应来源引用及读取内容 | 提供给 Agent 阅读，或按明确规则处理 |
| 变更集 | 待新建、关联、修改的内容及其依据 | 约束检查、写入及变更记录 |

这些类型不必全部成为独立 API 数据结构，也不要求所有字段都在每次返回中展开。候选方案可以通过保留引用、按需读取细节来控制体积。

当前原型的 `neighbors` 主要是供 Agent 阅读的关系描述字符串。若后续需要算子直接组合，应考虑同时提供结构化端点、类型和必要属性。这个考虑尚未落实为接口修改。

还需区分两种“证据”：候选检索中的通道名次和分数说明为什么召回；原文、实验及检查记录说明知识来自哪里、已有支持关系是什么。二者不应在后续组合中混为一类。

### 4.2 算子、视图与工具的关系

一个对 Agent 暴露的工具可以调用多个基础操作；一个逻辑算子也可以有不同的索引实现。模型相关的参数化视图可以作为复合算子，但不必每个视图都单独注册成工具。

算子不以内部步骤少为必要条件。需要避免的是：把开放的理解任务放入内部，再以固定 JSON 输出宣称其语义已经明确。

## 5. 备选的接口组织方案

以下方案可以组合使用，尚未选定。共同前提都是由外部 Agent 作出语义判断。

| 方案 | 主要接口形态 | 优点 | 需要解决的问题 |
| --- | --- | --- | --- |
| A：以通用基础操作为主 | 候选检索、记录读取、遍历、匹配、集合处理和显式写入 | 接口较少，组合灵活，易观察每步结果 | Agent 需要掌握较多路径和模型约定；重复组织常用上下文可能增加调用与出错机会 |
| B：基础操作加模型相关视图 | 在 A 上增加共同命题的主张、问题回应、资源使用记录、实验上下文、依据追溯等视图 | 将反复使用的路径、关系角色和返回约定固定下来 | 如何选择必要视图、控制接口数量，以及处理信息缺失与结果体积 |
| C：显式查询表达式 | Agent 提交结构化的图模式、投影、筛选与分组表达式，系统检查后执行 | 一次表达多步访问和连接，适合复杂查询 | 表达式能力范围、错误反馈和约束检查；是否值得设计专门格式，还是使用现有查询语言 |

讨论中较值得先检查的是 B：用少量基础操作承载通用访问，再从具体任务中识别值得固定的模型视图。这只是备选倾向，不是已决定的架构。C 也不意味着系统要包含 LLM 查询规划器；查询表达式由外部提供。

### 5.1 基础操作草案

| 操作族 | 输入 → 输出 | 边界与状态 |
| --- | --- | --- |
| `find_entities` / `find_statements` | 查询内容与类型限制 → 排序候选 | 已有原型；只召回候选，模型调用边界待约定 |
| `get_records` | 节点或关系引用、所需字段 → 已存储记录 | 候选；按引用读取，不重新生成描述 |
| `traverse` / `match` | 起点或图模式、类型与关系约束 → 节点、关系或匹配结果表 | 候选；沿已有关系执行，不因路径可达而推出新语义关系 |
| 筛选、投影、连接、分组、聚合、排序 | 记录表与显式字段、键、条件 → 结果表 | 候选；使用可执行规则，不能默默从 description 中推断未结构化的值 |
| `trace_evidence` | 节点或关系、明确的追溯范围 → 来源引用与已有依据联系 | 候选；来源定位、支持关系和核验记录保留各自含义 |
| `read_source` | 来源引用 → 原文内容块 | 所需配套访问能力；已有材料工具如何接入、是否单列为系统算子待定 |
| `apply_delta` | 明确变更及依据 → 写入结果与变更记录 | 候选；负责结构与引用约束，不判定新知识是否真实 |

通用集合操作可以交给现有数据库或代码执行，不因列入概念算子库就要求重新实现它们。上述操作能否共用统一的结果表，也是待讨论事项。

### 5.2 从模型导出的访问视图草案

| 候选视图 | 依赖的模型结构 | 返回内容与关键约定 |
| --- | --- | --- |
| `claims_of_concept` | Claim 经 `EXPRESSES` 连接 ClaimConcept | 返回已关联的具体 Claim 与来源；不在查询时重新判断命题等价 |
| `responses_of_issue` | Claim 经 `RESPONDS_TO` 连接 Issue | 返回回答、已有 stance、关系描述与依据；缺少 stance 时不自动补判 |
| `resource_records` | ResourceRecord 经 `DESCRIBES` 连接 Resource，并保留论文归属 | 并列返回各论文中的描述与使用记录，不合并成一条无来源的统一说法 |
| `experiment_context` | Experiment 的 `EVALUATES`、`USES`、`MEASURED_BY`、`ON_TASK` 等联系 | 返回被测对象、资源角色、指标、任务、描述与锚点，不判断实验可比性 |
| `observations_of` | Observation 的 `OBSERVES`、`CHECKS` 联系 | 返回已存储的检查发现、时间、目标版本和核验关系；不把任意一次观察扩展为长期有效状态 |

这些视图应当能由明确图路径、连接和投影实现。是否独立命名、使用统一的视图参数，或完全交由图模式表达，仍由第 5 节的方案选择决定。

模型有意保留的区别需要落实到返回语义：

- 共享对象身份与具体论文记录同时可追溯；Claim 可被查询和引用，不因此与另一篇论文的 Claim 合并。
- 同一 Issue 下的回答与同一 ClaimConcept 下的主张，沿不同关系取得，不能混用。
- 论文层面的资源使用关系不自动推为某项 Experiment 的使用角色；同一 Resource 也不足以确定某条 ResourceRecord 描述的就是该实验设置。
- 关系上的 description 和 anchor 可能承载重要限定，不能只取两个端点就丢掉这些内容。
- 当前许多条件仍在描述中。系统可以返回这些文字，但不能据此声称已经取得完备的结构化条件或完成可比性判定。
- Observation 保留独立检查的时间和范围，不要求隶属于某一篇论文；作者报告与检查发现分别呈现。

## 6. 用具体研究意图检查组合

以“两个方法都在同一个 benchmark 上报告收益，它们能否直接比较”为例，先分开数据访问与研究判断：

| 步骤 | 执行者 | 输入与产出 |
| --- | --- | --- |
| 定位对象 | 系统候选检索，Agent 选择 | 根据称呼返回方法与 benchmark 候选，由 Agent 确认对象身份 |
| 查找实验 | 系统 | 按已确认 ID 匹配实验及资源角色；返回匹配记录和路径 |
| 取得设置 | 系统 | 展开实验上下文，返回资源、指标、任务、描述及依据位置 |
| 判断还缺什么 | Agent | 阅读记录，识别需要回查的切分、候选集合或后处理等内容 |
| 回查原文 | 系统提供材料，Agent 阅读 | 根据锚点读取相应设置与结果材料 |
| 判断可比性 | Agent | 形成比较结论、未知项与双方依据 |
| 积累新理解 | Agent 提交，系统写入 | 在新判断的表示方式明确后，提交显式变更并保存来源 |

这里不预设两个实验最终可比，也不要求每次都走完整流程。已经取得足够信息时可以停止，信息不足时由 Agent 决定继续访问什么。

当前模型对 Agent 自己形成的跨论文判断如何归属仍需细化。不能为了打通写入流程，把这个判断错误地归给某篇论文，或写入只用于简短提醒的 note。这个例子因此同时检验访问接口和数据模型的表达边界。

上下文预算也需要单独考虑。系统可以按照明确优先级、数量限制和路径规则截断，并说明哪些部分未展开；决定某项条件对当前研究问题是否关键，仍由 Agent 承担。无 LLM 的组装算法可以作为候选，但需要先定义目标与约束，不能从 `assemble_context` 这个名称直接推定其能力。

## 7. embedding 与“无 LLM 参与”的实现边界

当前 `find_entities`、`find_statements` 原型内部调用 Qwen3-Embedding-8B 编码查询，并使用库中向量进行检索。这个事实需要明确记录，不能把现有原型写成完全没有模型调用。

已明确的要求是：系统不使用 LLM 理解任务、决定身份、判断关系或生成结论。embedding 编码是否也必须移出服务，需要进一步明确；不能默认它已经获得例外。

| 处理方式 | 系统与外部的分工 | 影响 |
| --- | --- | --- |
| 外部生成向量 | 外部提供查询向量及对应编码配置；节点向量也在外部生成或作为派生数据提交，系统负责索引查询与融合 | 满足算子内部完全不调用模型的严格边界；需要校验向量空间及配置兼容性 |
| 内部保留检索编码组件 | 仅允许固定 embedding 编码，不允许 LLM 判断、重排解释或生成 | 保持当前按文本调用的便利，但需要用户明确接受这个例外，当前未定 |

讨论阶段可以先按最严格口径描述逻辑操作：系统接收查询文本用于词匹配，接收外部向量用于向量查询。向量编码位置与检索操作语义分别说明。本稿未据此修改原型或决定迁移方案。

无模型调用也不自动意味着检索完备或结果在任何环境都完全一致。近似索引、排序并列、数据状态和截断参数仍影响输出，应作为执行约定记录。相似度与排序分数不代表身份成立或主张得到支持。

## 8. 研究定位与下一步

算子体系需要解释模型如何被使用，但不要求每个算子都是新算法。当前候选查找文档已将标识匹配、混合召回和融合定位为工程组件；本次讨论不改变这一定位。

尚需回答：相比让 Agent 直接写图查询、调用通用工具或读取文本记录，模型相关操作是否减少了路径使用错误、来源混淆和必要信息遗漏，是否让已有理解更容易被正确复用？这些是评价候选，不是已证明的收益，也不是已确定的实验协议。

可能需要区分数据内容本身的收益与访问机制的收益。更丰富的知识、更好的模型或更高的访问预算，都可能影响任务效果，不能全部归因于算子设计。是否研究结果组织、约束维护或访问成本，应由实际任务中的问题来决定。

下一步建议按以下顺序收敛，而非立即实现整套库：

1. 选择一个已经写入研究设计的意图，列出 Agent 真正需要取得的记录、关系和依据。
2. 写出一份预期返回样例，明确 ID、角色、来源、未知与截断如何表示。
3. 对照通用基础操作、模型视图和显式查询表达式，选择足够完成该任务的接口组合。
4. 明确 embedding 的执行边界，以及写入新理解所需但当前模型尚未表达清楚的部分。

待这些问题收敛后，再决定哪些内容进入正式算子设计、哪些只是外部 Agent 的使用约定，以及哪些机制需要通过实验检验。
