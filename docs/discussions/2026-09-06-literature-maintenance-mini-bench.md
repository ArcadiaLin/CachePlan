## 1. 定位与当前共识

目标是构建一个 **agentic 文献资源系统构建与维护 benchmark**，服务于以 CachePlan 为主要技术贡献的研究：

> 给定论文及相关资源构成的版本化证据环境，让参评方法在评测过程中逐步构建和维护一个文献资源系统；以最终系统快照及其对固定 DAG 工作流、下游 Agent 工作和 QA 的支持能力评价成果质量，同时评价获得这些成果的构建成本与执行效率。

**基本评测单位是一段系统构建过程及其最终成果。** 多次加工与维护的结果积累到同一系统中，最终验收这个系统能够承担哪些工作。QA 是验收方式之一；单条回答、局部抽取分数或调用费用不足以代表系统成果。

论文和关联资源内容应成为数据集本体，访问方式应可控制，结果和成本应可复核。Mini-bench 提供真实工作负载、独立质量标准和可复现环境；论文主线是 CachePlan 的执行优化机制及其相对强基线的效果，不要求 mini-bench 同时达到一篇独立 benchmark 论文的规模或贡献要求。

当前认可的方向包括：

- 候选规模为 **约 50 篇论文及相关资源**。ACL 2025 是候选来源，会议、篇数和是否删减均未确定。
- 保留较丰富的数据模型和深加工目标；控制首版规模不等于把任务削成浅层抽取。
- 以系统级多任务、批量执行为 CachePlan 的主要评测场景，让 agent 作为算子参与构建；研究可复用前缀、合法调度选择与有限 KV 容量竞争共同带来的优化空间（文献依据见 §8.5）。
- 构建成果以系统快照交付，通过固定 DAG 工作流、下游 Agent 工作及 QA 等方式验收，具体能力合同尚未冻结。
- 下游 Agent 支持度主要评价任务完成情况与产物质量，不以该 Agent 的运行效率作为严格评分依据；构建成本和构建执行效率另行计量。
- 技术资源抽取以 precision、recall、F1 为主要质量依据；其他产物也需要明确的质量判据。
- 将真实关联仓库中需要的内容下载并固定为数据集的一部分，必要时检查历史 commit。
- 空仓库、交付不完整和长期未更新等真实情况是重要样本，不应为了“干净”而排除；其具体含义需要人工核验。
- 采用可控的访问环境，支持固定格式的检索工具接口；本地文件检索或自定义检索方式的具体协议待定。
- 评测支持 GPU 执行信息或 API 调用信息，为质量—成本分析及 CachePlan 研究提供观测。

以下章节将这些方向展开为候选设计，不将尚未讨论清楚的接口、阈值、数据划分或算法写成既定规格。

## 2. 应用对象与资源模型

应用模拟一个使用 agent 对论文进行深度加工、管理和服务的文献资源系统。输入为 PDF 或其他格式论文及关联材料；多次执行形成可持久化、带证据与版本的记录和关系，并共同支撑下游工作。最终交付范围由系统能力合同决定。

### 2.1 技术资源

沿用 P4A 项目的分类思路，当前目标类别为：

`dataset | benchmark | code | model | tool | protocol | skill`

除类型外，候选字段包括资源身份、别名、链接、版本、证据位置，以及论文与资源的角色关系：提出／发布、使用、比较或仅提及。实际 schema、类别边界、未知类型的处理与历史 P4A 模型的兼容方式仍待确定。

同一实体可能承担不同角色；论文中的声称和外部核验结果应分别存储，不能将“论文说已发布”直接当成“已确认交付”。

### 2.2 文献资源

用户提出的目标范围包括：

- 摘要、元数据、章节结构；
- 核心观点／Claim、术语；
- 实验描述，包括 Method 与流程图；
- future work、contributions；
- 引用文献及其引用上下文（Cites + context）。

候选细化方式：

- 区分原文摘要与生成摘要，分别评价信息提取和综合表达。
- 将实验描述拆为方法流程、实验配置和实验结论；记录数据集、基线、指标、设置与结果之间的关系。
- 将方法流程图视为结构化方法图的呈现：优先评价节点、依赖和证据，而非图像外观。
- 将 Claim 与支持它的正文、表格、图或实验结果关联，避免只提取无来源的概括。

丰富的数据模型不意味着第一版必须对每个字段提供同样规模的人工 gold。建议区分基础字段、核心深加工和扩展表达三个评测层；最终纳入主分数的字段尚未冻结。

### 2.3 深度整合与持久化状态

整合对象包括：论文与仓库的对应关系、资源交付情况、跨论文实体归一、引用与被引关系，以及证据和版本依赖。

库内被引关系可以由库内引用边反向得到；外部被引信息需要独立声明来源、覆盖范围和观测时间。不能将小语料内部的被引关系或计数当作全局引文网络。

持久化记录需要支持追溯来源、识别输入版本，以及更新后区分受影响和未受影响的内容。具体存储系统与事务实现不在本轮决定范围内。

### 2.4 最终系统成果快照

系统快照是构建阶段的交付对象，需要能够标识当时的记录、关系、证据、版本及验收所需的系统状态。索引、配置和服务接口等是否纳入交付、如何打包和恢复，取决于后续确定的能力合同；本轮不指定存储实现或完整应用架构。

快照质量既包括内部数据正确性，也包括这些成果是否足以支持下游工作。局部记录正确但未正确整合、缺少必要关系或混用资源版本，都可能使最终系统无法满足验收要求。

## 3. 评测过程：逐步构建与成果验收

论文数量只是语料规模；真正的构建 workload 由事件与任务组成。评测分为构建和成果验收两个阶段：构建阶段持续加工和维护，交付系统快照并记录整体消耗；验收阶段在统一条件下评价快照能够支持的工作。具体任务族如下：

| 阶段与任务族 | 应用行为 | 需要验收的结果 |
|---|---|---|
| 构建：新增入库 | 解析论文，抽取资源和证据，核验、消歧、关联并发布记录 | 记录与关系正确、证据充分、结构及版本一致 |
| 构建：增量维护 | 接收新论文、新资源版本或新证据，识别并更新受影响内容 | 预期变更完成，未受影响内容不被误改，来源可追溯 |
| 验收：固定 DAG 工作流 | 使用建成系统执行预先定义的下游工作流 | 必要信息与能力可用，工作流完成且输出正确 |
| 验收：下游 Agent 工作 | Agent 借助建成系统完成指定工作 | 任务完成、产物正确且证据充分；支持度不严格评价该 Agent 的运行效率 |
| 验收：检索问答 | 针对明确的系统快照检索、比较并组合证据 | 答案及证据正确，覆盖必要信息，无答案时正确处理 |

固定 DAG 指用于验收系统支持能力的下游工作流，不要求构建阶段采用同一个固定 DAG。下游工作流、Agent 任务和 QA 的具体集合及其权重仍待确定。

一个示例服务需求是：

> 哪些论文在数据集 D 上使用了评测协议 P，论文对应版本的代码是否提供评测入口？请给出论文依据和仓库文件依据。

这个需求可以自然驱动实验理解、资源核验、实体归一和跨论文证据整合。它仅用于说明任务形态，不是已经选定的测试题。

候选构建骨架：论文解析 → 候选资源／事实抽取 → 按资源展开核验与证据整合 → 验证及有界修复 → 发布／更新记录；多次构建任务共同形成待验收的系统快照。核验、抽取和链接可以存在并行分支；具体算子边界与可重排条件待定，不要求每篇论文运行相同数量的步骤。

为了体现“维护”而非一次性批处理，建议首版包含至少一种可回放的真实更新事件。检索问答先考虑答案集合与证据可人工确定的题型；开放式综述是否纳入主评测仍待讨论。

## 4. 数据集本体：论文与真实资源快照

### 4.1 采集与交付原则

论文、关联仓库及其他必要资源组成可下载的证据环境。人工 gold 和评测专用判断依据与 agent 可访问材料隔离；原始材料本身可以包含正常用户可见的信息。

采集应基于真实论文中的链接，记录来源、采集时间、版本标识、文件清单和内容 hash。仓库内容固定到明确的 commit；若选择历史版本，需预先声明时间／版本选择规则，而非按失败程度挑选。

“下载需要的内容”不应退化为只保留人工已认定有用的文件，否则数据集已经替 agent 完成定位。建议采用公开、可复现的范围规则，保留必要目录结构、说明及候选文件，记录排除项。大文件、外部下载、子模块及分发权限需要单独确认；尚未决定完整镜像还是受控子集。

### 4.2 不完善资源是重要评价对象

应保留并人工区分：

- 仓库确实存在但为空；
- 只有说明或发布承诺，缺少声称交付的内容；
- 部分代码、配置、数据或权重缺失；
- 长期未更新，但可能仍完整可用；
- 采集时链接失效、权限受限或请求失败；
- 证据不足，无法确定状态。

长期未更新不自动意味着不可用；访问失败不等于空仓库。失败状态需保存实际响应与观测时间，不能统一替换成空目录。

核验可以区分身份对应、内容交付、运行入口与配置、实际执行和实验复现等层次。首版承诺核验到哪一层尚未确定，不能把静态文件检查写成执行成功或复现成功。

历史源码快照与完整历史外部环境也要区分：固定 commit 不代表已经还原当时的下载链接、权限、依赖与服务。无法还原的部分应明确标记；源码版本时间与外部状态观测时间分别记录。

正确识别“未发布／不完整／未知”可以是成功完成任务。资源不可用不应直接计作 agent 失败。

## 5. 访问与检索协议

目标是控制可见证据和工具行为，同时保留 agent 自主调查的空间。标准接口不等于固定推理流程。

候选主协议为“本地快照＋标准访问工具”，统一：

- 可访问范围和资源版本；
- 列目录、搜索、读取等操作的输入输出格式；
- 分页、截断、错误语义与证据定位方式；
- 调用记录及返回内容的可追溯性。

agent 仍决定查什么、查询词、读取顺序、何时交叉验证，以及证据不足时如何继续调查。具体工具名称、schema、检索算法和预算尚未设计。

用户也提出允许在 bench 内自定义检索方式。候选组织方式是将其作为单独配置或评测轨道；若检索权限与工具能力不同，不应与固定接口结果无条件混排。是否开放 shell、是否允许外网访问及如何验证访问边界，需要在协议中明确。

论文解析、全文索引、向量索引等准备工作的责任边界也要固定：由 bench 提供的公共准备与参评系统自行进行的预处理分别记账，避免隐藏一次性成本或额外信息优势。主对照中的工具延迟与失败回放方式也需一致。

## 6. 独立真值与系统成果质量评分

### 6.1 主要评价维度

| 维度 | 候选评分依据 | 边界 |
|---|---|---|
| 最终系统快照 | 数据、关系、证据与版本一致性，以及下游所需能力是否具备 | 不能以若干局部抽取分数代替整体成果验收 |
| 固定 DAG 工作流支持 | 工作流完成情况、输出正确性、必要信息与能力覆盖 | 评价建成系统对下游工作的支持，不规定构建方法的内部 DAG |
| 下游 Agent 支持 | 指定工作完成率、产物质量与证据充分性 | Agent 运行效率不作为支持度的严格评分依据 |
| 技术资源抽取 | 实体、类别与角色关系的 precision／recall／F1 | 需定义实体匹配、别名、重复项与标注覆盖范围 |
| 基础记录 | 规范化字段匹配、章节与引用结构完整性 | schema 通过不等于内容正确 |
| 证据归因 | 事实、Claim 或关系是否被指定位置支持 | 有证据链接不等于证据支持结论 |
| 资源核验 | 身份与交付状态判断正确率或分类指标 | 区分不可用、未知与未检查 |
| 增量维护 | 预期变更、版本／引用一致性、未受影响记录保持情况 | 不能只评价更新后的局部新字段 |
| 检索问答 | 答案集合、证据覆盖与无答案处理 | 开放式文本不能仅靠字符串匹配 |

系统成果及其支持能力是质量评分的落脚点；字段与关系指标同时用于检查内部正确性和定位失败原因。不急于压缩为单一总分。各类下游验收的权重、字段权重、micro／macro 聚合、系统及任务合格门槛与缺失处理方式需事先确定，而不是看完方法结果再选择。

### 6.2 人工核验与裁定

人工 gold 应包含资源身份与角色、论文证据位置、对应快照，以及支持状态结论的文件位置或明确的缺失判据。

“没有搜索到”不自动证明不存在；负例需有声明的检查范围，无法裁定时保留未知。未覆盖的标注不能当作负例，否则 precision 和 recall 都可能失真。

开放语义任务需要标注规则与人工复核／分歧裁定机制；模型评审可以辅助，不作为唯一真值。标注人数、抽检比例、开发与测试划分、gold 的发布方式尚未确定。

### 6.3 构建与验收的边界

候选验收协议是在交付后冻结系统快照，统一下游工作流、Agent 配置和可访问范围。应区分读取已有成果完成工作，与重新读取原始材料补做构建：不能在验收时悄悄补齐缺失记录，再将补建后的能力算给原快照。具体是否允许访问原始材料、允许哪些临时计算和状态写入，需在合同中声明。

支持度评价以任务完成和产物质量为主。统一验收条件用于减少下游 Agent 自身能力与配置的混杂，不意味着把该 Agent 的速度或费用计入支持度分数。验收开销与构建开销分别记录；若以后评价建成系统的服务性能，应单列指标。

## 7. 构建执行记录：成果质量与 GPU／API 成本共同报告

评测协议应原生支持执行观测，但不能假设所有后端都有同等可见性。

### 7.1 通用记录

建议关联任务、算子、模型请求和工具调用的 ID，记录输入／状态版本、起止时间、重试、修复、失败及最终质量结果；保留模型与运行配置、工具版本和必要的可复现信息。

构建总成本包含失败、重试和修复，而非仅成功调用，并覆盖形成交付快照的整段过程。模型成本、工具／检索成本、准备成本与端到端时间分开报告；成果验收阶段单独记账。

### 7.2 本地 GPU 推理

候选记录包括硬件及服务配置、实验资源占用时间、显存／KV 占用、队列等待、prefill／decode 耗时和后端支持的缓存统计。哪些值可直接观测、哪些是采样或估算，应逐项说明。

GPU 时间需声明计量口径，例如分配的 GPU 数乘实验持续时间，与 kernel 活跃时间不是同一个指标。并发运行中，整段实验计量与逐请求归因分开；不能将重叠请求的 wall time 简单相加作为 GPU 时间。

### 7.3 API 推理

记录模型标识、请求参数、返回的 usage、延迟、错误与重试，以及有来源的实际费用或估算。供应商未暴露的 GPU 时间、KV 驻留或缓存统计应标为不可观测；未返回的字段不能当作零。费用估算注明价格来源与时间，不能冒充实际账单。

### 7.4 联合报告

**主结果围绕获得系统成果的代价组织。** 候选比较包括：在相同成果质量和下游支持能力要求下，交付系统快照的总构建成本与完成时间；在相同资源预算下，能够交付的系统完整程度和下游支持能力。具体质量门槛、预算和聚合方式待定，不能将高质量、高成本与低质量、低成本直接排成无条件的优劣。

构建阶段的合格任务吞吐、端到端延迟、尾延迟及每个合格任务成本作为补充，解释整体交付表现。始终同时给出系统能力、局部质量分布、失败率和总完成量，避免局部节省或“每个成功任务成本”掩盖未完成的系统建设。

输入 token 数、缓存命中率和工具调用数作为解释性指标，不单独代表执行效率。API 费用与本地 GPU 时间分别报告，不未经声明换算就作等价比较。

## 8. 与 CachePlan 研究的关系

仓库的暂定目标是 SIGMOD；CachePlan 的候选角色是文献维护系统内的执行优化器，探索 agent 算子调度与 KV 保留／淘汰的协同。SGLang 是计划中的后端，LRU 是重要基线，能力需对固定版本验证。

**论文主贡献是 CachePlan，mini-bench 是支撑方法研究的工作负载与评测环境。** 目标是在该环境中，相比适用的先进方法及强基线，以更低成本、更高效率构建具有同等或更好支持能力的系统。“取得 SOTA”需要由明确的比较对象、公平条件、机制归因和不同运行条件下的结果支撑，当前没有这样的效果结论。

Benchmark 定义正确完成业务的条件与可观测环境，不要求参评方法采用 CachePlan 的编排方式，也不以证明 CachePlan 有效作为数据集选样条件。

### 8.1 保留真实深度，不制造重复工作

用户希望流程具有足够深度与复杂性，为优化提供研究空间。判断原则是：拿掉 CachePlan 后，这一步是否仍服务于业务验收条件？

合理复杂度可以来自跨章节证据、论文与仓库信息冲突、多名称／多版本实体、调查中显露的分支、更新传播与有诊断依据的修复。不应通过固定多轮讨论、无条件互审或反复抽取已验收事实来制造调用与缓存命中。

### 8.2 静态前缀也可能存在动态驻留决策

本轮提出的研究范围补充是：共享前缀不一定必须动态生成。即使内容固定，只要后续调用、复用时机与生命周期逐步显露，应用信息仍可能帮助调度或驻留管理。

这与 [OQ3](../open-questions/Multi-run-workloads.md) 中强调“超出静态模板的动态上下文构造”有所区别；本文记录这一候选扩展，不将 OQ3 标为已解决，也不改写原问题。

候选信息包括工具等待后的续用机会、已就绪的同前缀工作、分支展开和任务完成状态。实际收益必须由 token 前缀、驻留情况、等待代价与缓存压力证明，不能由任务名称相同或流程较长推断。

### 8.3 比较与归因边界

- 保留完整、同信息内容的强静态前缀和简单局部性调度基线。
- 分开检验算子调度、后端请求调度、保留／淘汰及 prompt 重构，再评价联合效果。
- 分别记账 prompt／KV、artifact／result 和 plan reuse，不重复计算收益。
- 各策略具有相同的合法结果复用机会；增量维护减少无关重建工作的收益，不直接归因于 KV 调度或驻留。
- 调度遵守依赖、版本和共享状态冲突；未来信息只在其实际可见时提供给在线策略。
- 描述真实 prefix root、上下文长度、到达／等待、分支和工作集分布；50 篇论文不自动意味着足够的复用或缓存压力。

### 8.4 与 AstaBench 的关系及候选评测贡献

[AstaBench v2（ICLR 2026）](https://arxiv.org/abs/2510.21652v2) 提供科学任务、受控工具、质量—费用报告和广泛 baseline，值得借鉴。它不仅包含 QA，也有结构化综述表、仓库执行、任务内 stateful notebook，以及评价报告、代码和产物的 E2E 任务（§3–4、Appendix E，尤其 E.9；PDF pp.5–7、32–42）。因此，结构化输出、多步执行、有状态工具或产物与成本联合评价本身，不足以构成我们相对它的区别。

**当前需求的区别在于评测组织与成果对象：多次构建操作积累到一个持续存在的文献资源系统，交付快照后，以一组下游工作验收该系统的支持能力，并评价获得这种能力的整体构建代价。** AstaBench v2 的任务及评分定义没有建立这套合同，不能直接承担我们的主评测。这个判断限定于论文所述 benchmark，不扩展为对 Asta 整个产品能力的判断。

相应的候选贡献是：面向 agent 驱动的文献资源系统构建，定义以最终系统能力为质量对象、以整体构建代价为效率对象的工作负载与评测协议。它可以作为 CachePlan 论文的工作负载与评测贡献，不要求独立发表 benchmark，也不要求在功能或规模上超过 AstaBench。相对 AstaBench 的区别不等于全领域新颖性已经成立；是否已有相近评测方式仍需针对性核对，不作“首次”声明。

### 8.5 为什么以系统级多任务、批量执行为主要场景

**2026-09-07 补充的研究判断：单 session 历史前缀复用提供基础收益；多任务执行中的调度选择、工作流信息和有限 KV 容量竞争，为缓存管理与编排的联合优化提供额外空间。** 这是 mini-bench 将任务放进同一系统、让 agent 作为算子发挥作用的理由之一。

单个串行 coding session 的典型收益是复用既有对话历史，减少重复 prefill 的计算与等待；如果只有一条严格依赖链，应用层改变执行顺序的空间有限。系统级执行则可能同时拥有多个合法就绪算子：调度改变复用发生的时间，驻留状态改变执行某个算子的代价，工具等待又带来保留与腾出空间的选择。此处的 batch 包括一批输入的处理，也包括多个持续到达、同时在途的工作流，不要求所有请求一次性已知或同时提交。

本地论文集中有以下直接证据。数字均来自各论文的实验配置，不是 CachePlan 的结果，也不是可直接套用到本 mini-bench 的收益预测。

| 文献与位置 | 原文证据 | 支撑的判断与边界 |
|---|---|---|
| [Helium](https://doi.org/10.1145/3802046)，§7.4 / Fig.8，p.18；Table 4，p.17；§7.6，pp.21–22 | Trading 输入批量从 8 增至 80 时，相对 LangGraph 的优势扩大；调度对照中，相比 LSPF，延迟从 188.93 s 降至 149.76 s（约 1.26× 加速），命中率从 37.9% 升至 56.5%；案例中相对 LangGraph 的平均推理 batch 请求数为 1.18× | 批量工作流及算子可见性提供跨查询优化机会。Table 4 关闭的是 proactive KV caching 与 prompt caching，以隔离调度，不能理解成完全没有 KV 复用；其主要依赖可预先分析的工作流结构 |
| [CacheWise](https://arxiv.org/abs/2606.16824v1)，§6.1–6.2 / Figs.13–14，pp.8–10 | 同一推理实例并发运行多个 coding session；在其配置中，低负载 N≤10 时各策略性能接近，高负载 N>10 时相对 vLLM 与 InferCept 报告约 2.7–3.5× session 完成时间加速，token goodput 提高 1.64–2× | 缓存竞争较小时管理策略的增量收益有限，竞争增大时差异显现。并发阈值属于其配置；实验为轨迹重放，session 完成时间明确排除工具执行时长，不能等同于完整业务耗时 |
| [TOPAS](https://arxiv.org/abs/2608.25523v1)，§II / Table I，p.2 | 两个 agent 使用不同长前缀，保持请求集合、动态后缀、输出长度及 KV 预算相同，仅改变分组／交替执行顺序。每个 agent 各 100 个请求时，分组／交替的总完成时间为 1145.5／2086.0 s，平均运行 batch 为 9.3／4.7 | 执行顺序通过前缀共驻留影响动态 batch 容量和整体效率。该微基准不能推出所有工作流都应按 agent 分组；仍需兼顾依赖、任务进展与公平性 |
| [PBKV](https://arxiv.org/abs/2605.06472v1)，§6.1–6.2 / Table 1，pp.6–7 | 三类工作负载分别采用 72／24／48 个并发 workflow，明确通过并发形成内存压力来评价缓存管理；动态工作流相对 LRU 最高约 1.85× 加速，指标为提交至完成的 workflow 延迟 | 动态后续调用和生命周期信息可用于管理有限 KV。它已有多步预测、跨 workflow 复用估计等机制，是 CachePlan 需要区分和比较的近邻，不能把这些概念本身作为新贡献 |

可复核的本地原文：[Helium](../../references/papers/2026-Helium/source.pdf)、[CacheWise](../../references/papers/2026-CacheWise/source.pdf)、[TOPAS](../../references/papers/2026-TOPAS/source.pdf)、[PBKV](../../references/papers/2026-PBKV/source.pdf)。这些本地副本不随 Git 分发，公开版本入口见上表。

其中应区分两类多任务收益：

- **跨执行共享前缀**：多个执行复用同一 procedure、contract 或材料前缀，顺序影响共享状态能否及时复用；相同语义或算子名称不保证相同 token 前缀。
- **跨执行管理驻留**：即使各 session 主要复用自己的历史，多个 session 仍竞争同一 KV 容量，管理器可以利用工具等待和预计续用时间决定保留对象。CacheWise 支撑的正是这一类场景；多 session 管理不要求 session 之间都有很长的公共前缀。

其他相邻证据需要单列机制：[CoDec](https://doi.org/10.1145/3802028) 利用专门 kernel 合并 batch 内共享 KV 在 decode 阶段的重复读取，可作为跨请求共享价值的补充，但不能直接计入普通 prefix caching 或 CachePlan 调度收益；[AlignedServe](https://doi.org/10.1145/3802009) 主要按 KV 长度对齐组织 batch，支持批量组织的重要性，不能用作前缀内容共享收益的直接证据。

**这些文献支撑选择多任务系统作为主要研究场景，但不证明“只有 batch 才有效”或“batch 越大收益必然越高”。** 个人应用也可能产生多分支或多 session；过高并发会加重淘汰与重计算。实际优化空间仍取决于 token 前缀结构、就绪宽度、工具等待、工作集与 KV 容量、prefill／decode 成本构成，需在本 workload 上刻画。未来对照应覆盖负载和容量变化，并保持输入、资源预算及合法重排条件一致。

文献也没有证明所有任务必须共同构建一个持久化业务系统。我们选择文献资源系统另有业务理由：让这批计算服务于共同、可验收的成果。系统快照及下游支持能力约束“工作是否做好”，整段构建成本、吞吐和完成时间检验“CachePlan 是否高效组织了这些工作”。因此，系统成果验收与多任务执行优化在本 mini-bench 中结合，但二者的证据职责仍应分清。

## 9. 下一轮需要收敛的事项

1. **语料与快照**：论文来源与数量、选样规则、历史版本选择、下载范围及分发权限。
2. **构建与交付合同**：初始状态、任务／事件序列、必须交付的资源与关系、核验深度、真实更新类型，以及系统快照的组成和恢复方式。
3. **成果验收与质量协议**：固定 DAG 工作流、下游 Agent 工作和 QA 的集合；支持度与系统合格条件；gold 覆盖、实体匹配、负例／未知、人工裁定、数据划分及分数聚合。
4. **访问协议**：构建与验收各自的访问范围、固定接口、自定义检索配置、预处理与外网边界，以及防止验收阶段隐含补建的规则。
5. **执行协议**：整段构建与单任务的时间／GPU／API 计量、验收开销分离、状态初始化、工具延迟回放、运行预算和重复运行方式。

候选下一步是先确定一个“逐步构建（含入库与相关更新）→ 系统快照交付 → 下游能力验收”的完整合同，再决定样本采集与标注安排。合同需要同时明确成果质量和构建代价，不能用一组 QA 代替全部系统能力验收；具体样本规模和验收任务尚未决定，也不在本轮启动实现。
