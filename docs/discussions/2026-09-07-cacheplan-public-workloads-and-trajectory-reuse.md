# CachePlan 研究重审：公开工作负载、轨迹复用与并发缓存优化

> **日期：2026-09-07。状态：方向讨论与候选问题，尚未形成方法、实验协议或正式方向决议。**
>
> 本文记录与导师讨论后对研究路线的重新审视，承接[文献系统 mini-bench 计划](2026-09-06-literature-maintenance-mini-bench.md)和[工作流设计依据](2026-09-07-mini-bench-workflow-design-patterns.md)。现有 CachePlan 尚无完成验收的方法效果实验；本文中的适用性判断不等于已复现相关工作或确认创新。

## 1. 为什么需要停下来重审

用户指出，目前只有一个初步的“轨迹复用”想法，尚未形成核心方法实践。此前讨论逐步走向：设计文献系统 benchmark，为其增加公共准备和分叉工作，再研究怎样优化这些工作。这样容易形成循环：**设计 benchmark → 针对 benchmark 优化 → 为优化机会继续设计任务。**

导师提出的代表性与工程规模问题进一步暴露了风险：自建任务上的领先结果，不能自动证明方法具有外部适用性；抽象大量真实工作模式、建设数据和独立评价，本身可能成为另一项庞大的研究工程。此前助手顺着应用设计不断扩展方案，也没有及时把讨论拉回具体的系统决策。

本轮提出的调整是：优先考察已有公开任务与执行系统，把主要精力放回 CachePlan 能改变的决策及其价值。文献 mini-bench 可以作为补充应用案例的候选，不必预先承担通用 benchmark 的代表性责任。这是当前建议，不表示已正式取消原计划或确定改做 coding。

## 2. 公开 benchmark 如何成为 cache 工作负载

需要区分三个层次：

| 层次 | 提供什么 | 仍需解决什么 |
| --- | --- | --- |
| 公开任务集与评价 | 外部任务来源、输入和任务完成标准 | 本身未必包含固定 agent 调用轨迹 |
| Agent 执行框架或既有工作流 | 将任务变成模型调用、工具操作和依赖 | 同一数据集可因执行器不同而产生不同负载 |
| 系统负载协议 | batch、到达过程、并发、缓存预算和性能指标 | 必须固定公平条件，刻画适用范围 |

因此，采用公开数据集不能自动消除工作流设计偏差；但复用已有执行器及其业务策略，可以降低“专门为 CachePlan 构造任务”的风险。还需保留原任务质量评测，不能只借用数据集名称。

### 2.1 已精读 cache 论文的做法

| 论文 | 数据与执行工作负载 | 为系统评测做的组织 | 对 CachePlan 的参考价值 |
| --- | --- | --- | --- |
| PBKV | HoVer + LangChain；SWE-bench + AutoGen；FinanceBench + CrewAI | 前两类动态工作流，最后一类构成静态工作流以比较 KVFlow；增加并发产生缓存压力 | 最接近动态调用下的 KV 保留、淘汰和预取 |
| TOPAS | 三类合成 DAG；MetaGPT SoftwareDev 的真实 prompts | Chain-3、DAG-4、DAG-10-Wide；五角色 SOP、九阶段 TeamLeader 路径；统一到达轨迹和 SGLang 后端 | 最接近 ready 工作调度与前缀驻留的联合优化 |
| Helium | MMLU、TAT-QA、Amazon Reviews；另构造金融数据 | 五类基础工作流及组合 Trading 应用，按 batch 执行 | 已有批量工作流、强基线和执行组织的参照 |
| CacheWise | CATraces：真实 Claude Code 使用轨迹 | 确定性回放、多 session 并发；预测器训练／评测划分 | 适合服务层与缓存管理；固定轨迹不足以评价改变执行路径的效果 |
| CoDec | 合成 prefix tree、LooGLE | 将共享文档的查询分组，测试共享前缀树、解码计算和访存 | 适合底层机制，不能单独承载动态工作流主实验 |
| AlignedServe | ShareGPT、LongBench、AzurePublicDataset，及合成请求 | 组织异质长度请求和服务负载，测吞吐及 P99 TPOT | 适合请求服务层，对 operator 依赖覆盖不足 |

### 2.2 可以借鉴，但不能直接照搬的部分

- **PBKV 的组合方式值得参考，评价缺口仍需补齐。** 已读版本没有报告 HoVer 准确率、SWE-bench resolved rate、FinanceBench 答案质量；主服务实验的样本量和调用长度分布也交代不足。预测器的 1K 训练轨迹、500 测试轨迹不能当成完整主实验规模。[精读证据](../../references/papers/2026-PBKV/evidence_map.md)
- **TOPAS 的执行方式仍需核查。** MetaGPT 部分使用真实 prompts，但正文不足以区分完整执行、固定输出回放、按记录长度重新生成等方式，不能直接当作可复现的完整软件工程评测。[精读证据](../../references/papers/2026-TOPAS/evidence_map.md)
- **Helium 也组织了自己的工作流。** 它不代表“完全使用现成通用 benchmark”。其公开仓库列有五类微工作流、Trading、baseline 和运行入口，本轮只核查了公开说明，未复现。[官方仓库](https://github.com/mlsys-io/helium_demo)
- **CacheWise 的回放与计时口径要单独理解。** 它的 session completion time 排除了工具执行时长。我们应同时报告完整墙钟时间及分解项。公开仓库包含原始／解析轨迹、事件提取、分析和工具时间预测材料，不等于已核验完整服务实验可运行。[官方轨迹仓库](https://github.com/cachewise-project/cachewise-coding-traces)

代表性不只是样本总数，还包括共享前缀长度与范围、复用距离、工具等待、ready 工作数量、分支／重试，以及工作集相对缓存容量。Helium 的有界数据规模说明系统论文不一定要求工业团队级数据建设，但不能把其样本数量直接当作我们的充分性标准。

若研究目标转为执行与缓存优化，对 AstaBench 的判断也需要调整：它不满足此前设定的“逐步构建持久化系统”完整评价，并不意味着它不能作为 CachePlan 的任务来源。新的筛选问题应是能否接入统一后端、保留原评分，以及是否存在实际可调度的多任务执行。

## 3. “轨迹复用”想法的具体化与强对照

用户给出的例子：处理每篇论文前都要阅读 `paper-close-read` skill。能否先完成一次公共阅读，再让多个 session 继承这段历史，之后才分别提供论文？

```text
系统提示 → 要求阅读 skill → 工具读取 → 返回完整 skill
                                      ├─ 论文 A → 精读
                                      ├─ 论文 B → 精读
                                      └─ 论文 C → 精读
```

其核心是：**把任务无关的公共准备提前执行，在具体输入进入前建立可复用的会话分叉点。** 独立执行时，早期任务内容、工具调用措辞或调用元数据可能切断前缀共享；继承同一段规范化历史，有机会建立完全一致的 token 前缀。

“继承”意味着后续请求使用同一段公共消息历史；各分支之后独立发展。KV 能否复用仍取决于后端支持、token 与推理配置一致性、状态驻留或可恢复性，并非复制历史就保证命中。若公共准备还改变了文件或工具环境，也必须恢复对应环境状态。

需要分开计量：

1. 公共准备执行一次，省去重复模型调用或工具读取的收益。
2. 后续请求复用公共前缀 KV，省去重复 prefill 的收益。

最重要的强对照是：**直接将完整 skill 放入固定前缀，再接具体论文。** 如果阅读只是将文件内容装入上下文，这种静态方式可能已经获得相同共享，还省去准备轮次。模型不存在脱离消息历史和 KV、可以额外继承的“已读懂”状态。

因此，本例尚不能证明方法创新。只有公共准备确实产生不能由简单文件注入直接替代的有用状态，例如多材料读取、配置解析或中间产物，才值得进一步研究；这些产物也必须证明适用于各分支。即使如此，公共结果复用也应提供给适用基线，不能全部归功于 KV 优化。

讨论中区分的三个方向如下：

| 复用对象 | 改变的动作 | 核心问题 |
| --- | --- | --- |
| 历史结果／中间产物 | 跳过已完成工作 | 有效性与失效条件 |
| 历史执行路径 | 选择计划或从中间继续探索 | 适用性、探索多样性、恢复正确性 |
| 轨迹揭示的访问规律 | 指导调度与 KV 管理 | 相对简单策略的信息增益和决策价值 |

“用历史轨迹预测未来访问”与 PBKV 已有直接重叠；“公共准备后分叉”也不能仅因比原流程快，就成为足够的方法贡献。需要先指出现有方案未处理好的具体决策情形。

## 4. 公开 coding 任务中是否自然存在分叉

本轮定向核查发现了外部依据。以下 Agentless、SWE-Replay、Aider 材料尚未在本项目做完整精读或复现。

### 4.1 Agentless：定位之后生成多个候选补丁

Agentless 在 SWE-bench 上采用定位、修复、验证流程：逐步定位文件、函数和编辑位置，再采样候选补丁，通过测试和排序选择提交。官方复现说明包含每个 bug 生成 40 个候选补丁的设置。[官方实现](https://github.com/OpenAutoCoder/Agentless)、[复现说明](https://github.com/OpenAutoCoder/Agentless/blob/main/README_swebench.md)

```text
Issue + 仓库 → 定位 → 修复上下文
                         ├─ 候选补丁 A → 验证
                         ├─ 候选补丁 B → 验证
                         └─ 候选补丁 C → 验证
```

分支的理由是寻找正确补丁，独立于 CachePlan。但共享定位结果不等于已经验证共享 KV；需要检查真实请求的 token 前缀、原有缓存效果及剩余优化空间。

### 4.2 SWE-Replay：恢复历史中间状态，再分叉探索

SWE-Replay 归档此前的解题轨迹，选择中间步骤，恢复上下文与环境，再生成新的后续动作。在环境恢复上，它记录仓库差异，必要时回放动作；评测使用 SWE-bench Verified、Pro 和 Multilingual。[原文 §2–3](https://arxiv.org/html/2601.22129v1)

它直接支持“公开 coding 任务已有轨迹分叉需求”，同时也是我们必须面对的相关工作。本轮核查不能据此认定其提供了 GPU KV 驻留／调度的实验结论，也未确认可复用实现的完整性。

### 4.3 同一道题多次尝试，与不同题目共享准备，应分开

目前更明确的依据是同一 issue 的多个尝试。跨 issue 的公共工作仍需观察：固定工具说明适合静态前缀；仓库结构和公共模块可能共享，但受版本、相关性和内容顺序约束；针对某个 issue 的诊断不能直接用于另一个 issue。

SWE-bench 每个实例指定 `base_commit`，同仓库不代表同代码状态。[官方数据结构](https://www.swebench.com/SWE-bench/guides/datasets/) Aider 的 repo map 会按当前聊天状态选择相关内容，也不能假定每道题使用完全相同的地图。[官方说明](https://aider.chat/docs/repomap.html)

如果考察这些负载，应保留既有任务、分支预算和解题策略，先研究它们已经产生的执行机会；不能为获得更多 cache hits 增加候选数量或额外公共探索。

## 5. 现有研究是否主要靠增加并发

**增加并发是调度与 KV 淘汰研究的常见手段，但增加并发不等于制造共享前缀。** 它使多个请求同时可调度，并使多个会话的 KV 竞争有限容量。

| 研究 | 负载控制 | 检验目标 |
| --- | --- | --- |
| PBKV | 三类任务并发 72／24／48，并做敏感性分析；明确以并发诱发内存压力 | 动态调用下的保留、淘汰、预取 |
| CacheWise | 并发启动 N 个 sessions，逐步增加 N；报告 N≤10 时策略差异较小 | 多会话竞争下的调度与缓存管理；该阈值只适用于其设置 |
| TOPAS | 改变泊松任务到达率，各策略使用相同到达轨迹 | 负载变化下的调度和驻留决策 |
| Helium | batch 执行，改变 batch size | 跨工作流共享、执行顺序和并行性 |
| CoDec | 共享前缀树的形状、长度、批量规模等 | 已有共享结构下的解码计算效率 |
| AlignedServe | 真实／合成负载以及长短请求组成等 | 异质请求的 batching 和解码性能 |

各项依据见 §2 的原文实验部分。它们并未统一采用同一种并发协议；并发数、到达率与 batch size 也不是可以互换的参数。

### 5.1 跨 session 竞争不要求跨 session 共享

```text
Session A：模型调用 → 工具等待 → 下一次模型调用
Session B：模型调用 → 工具等待 → 下一次模型调用
Session C：模型调用 → 工具等待 → 下一次模型调用
```

即使三者只复用各自的历史，仍存在真实决策：A 等待工具时是否保留其 KV？是否让位给 B？B 完成后恢复 A，还是服务新请求 C？因此，多个独立 coding sessions 共享推理服务，就可能构成系统优化工作负载，无须共同维护一个业务系统。

这修正了此前一个过强前提：**不必先找到大量跨任务公共轨迹，才能研究 cache。**

| 候选方向 | 必须证明的事情 |
| --- | --- |
| 保留／淘汰与调度 | 原有执行中的历史复用与资源竞争存在可优化决策，且强基线尚未解决 |
| 重组轨迹以增加共享前缀 | 额外证明公共工作确实存在、重组合法、质量不受损，并优于完整静态前缀等简单方案 |

### 5.2 并发实验的解释边界

合理的评测应覆盖低负载、缓存紧张与接近饱和的区间，而不是只挑一个 LRU 表现差的点。各策略使用相同资源、任务和外部到达条件，保留工作流依赖与工具等待；闭环回放应由前一步完成触发后一步，不能无条件固定所有请求的绝对时间。

报告吞吐、完整任务延迟、尾延迟、排队、缓存压力和任务质量，命中率用于解释机制。低负载无收益也应保留。训练或调参使用的任务与最终评测任务应分开；轨迹长度或共享率的选择不能由 CachePlan 的效果反向决定。

固定轨迹适合比较同一批调用的服务成本；如果优化器改变 prompt、执行路径或分支生成，仍需真实执行评价这些变化。只按 token 长度合成请求，也不足以复现真实 token 前缀的共享结构。

## 6. 当前最值得澄清的问题

目前尚未确认一个超出现有工作的 CachePlan 机制。与其继续扩展 benchmark，更值得从公开执行中寻找一个具体实例：当前有哪些任务和缓存、哪些工作 ready、简单策略会怎样选择、额外信息为何让我们选择不同，以及究竟节省什么。

两个候选入口需要区分：

1. **多会话 serving。** 在原有 coding 轨迹中，工具等待、历史增长和 KV 竞争是否暴露 LRU、简单局部性调度、PBKV／TOPAS 等方案的剩余问题？
2. **已有分叉执行。** 在 Agentless 或 SWE-Replay 这类现成策略中，普通 prefix caching 和简单调度是否已经足够？若不足，具体原因是分叉点状态淘汰、等待期间的驻留，还是跨任务的资源竞争？这些只是待验证假设。

可以先做材料与实现核查，再讨论有界观察；本文不授权新实验目录、分析脚本或全量运行。后续是否采用某个 benchmark，取决于方法需要的执行自由度与可复现性，而不是它能否为预想机制提供更多公共轨迹。

当前应保留的研究态度是：**如果既有强策略已足够，就调整或放弃相应机制；只有确认真实执行中存在未解决的决策问题，才继续发展算法与评测。**
