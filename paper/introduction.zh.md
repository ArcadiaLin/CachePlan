# Introduction（中文讨论初稿）

> 2026-09-10。用于讨论立意与论证顺序，尚非投稿定稿。P4A 为暂用系统名；community 检测、摘要生成与检索机制尚未确定。下文提出研究问题与设计方向，不报告已实现能力或实验结论。相关工作引用及差异证据待补。

当 Agent 被用于文献调研、实验准备与方法实现时，它需要接触的研究材料会跨越论文、数据集、benchmark 和代码库。例如，为长上下文指令遵循实验寻找评测方案，需要理解评测目标与任务设置、找到适用的数据，并获取相应的评测工具。论文及其配套材料分别提供这些信息的不同侧面。因此，支持这类研究任务，需要帮助 Agent 从需求出发发现相关资源，并理解这些资源能够为后续工作提供什么。

这一需求涉及单个资源描述与集合背景之间的衔接。论文可能重点解释评测动机，数据集页面介绍数据内容，代码库说明运行方式；它们的表述重点和使用词汇并不相同。在上述例子中，一项查询可能直接匹配到 benchmark 论文，但要形成可供后续使用的材料集合，仍需定位相关数据与工具，并理解它们在这一需求中的作用。这引出一个问题：能否在独立资源描述之外，建立集合层面的检索依据，将相关材料的共同主题与各自用途呈现给 Agent？这种组织是否能比逐个资源检索更有效地支持研究资源发现，需要通过比较验证。

我们探索以资源 community 作为集合组织单元，并以 Agent 生成的摘要作为检索入口。一个 community 汇集围绕共同研究主题或使用需求的资源，其摘要综合成员材料，描述集合的主题、资源构成和使用背景。在长上下文评测的例子中，摘要可以说明该集合涉及的评测问题，以及哪些成员提供任务定义、数据或评测工具。检索系统据此定位相关集合，再向 Agent 提供具体资源与对应来源。集合摘要承担概括与检索的作用，资源记录则保留进一步检查和使用所需的信息。

实现这一思路，首先需要回答 community 如何形成。异构资源的文本相似性与它们在研究任务中的关联并不必然一致：论文和实现代码的描述可能差异较大，却服务于同一实验需求；主题相近的资源也可能适用于不同任务或设置。我们希望考察，如何在形成 community 时识别对资源发现有用的共同性，以及使用上的互补性是否能够提供有效依据。集合的边界同样重要：过于宽泛的 community 难以支持具体需求，过于狭窄的 community 则可能无法提供超出单个资源的背景。

其次，摘要需要同时支持集合概括和成员辨别。摘要若只突出主要主题，可能掩盖少数成员的重要特点；若将个别成员的能力概括为整个集合的能力，又会产生错误的使用预期。例如，集合中存在评测代码，不代表所有成员都具有可执行实现。摘要中的具体描述应能够对应到支持它的资源与材料，并在证据不足时保留不确定性。由此，摘要质量既涉及事实是否受到支持，也涉及是否保留了定位具体资源所需的信息。

最后，集合检索需要落实到资源发现。命中一个主题相关的摘要，并不意味着已经找到满足使用需求的数据或工具。系统需要使集合层面的相关性能够帮助定位成员，同时避免具体资源被摘要中的主要主题掩盖。因此，我们需要研究 community 摘要如何参与检索，以及它与直接资源检索如何配合。评价也应落在具体资源是否满足需求上，不能仅依据摘要的流畅性或主题相关性判断系统有效。

围绕这些问题，我们拟构建 P4A，一个面向 Agent 的研究资源组织与检索系统。系统以论文、数据集、benchmark 和代码库的基本记录及来源材料为输入，研究 community 形成、集合摘要生成和具体资源定位之间的配合。Agent 承担需要理解材料的组织与摘要工作，下游研究 Agent 通过检索结果继续检查和使用资源。我们的核心研究问题是：如何形成对检索有用的资源集合，并生成忠实且保留成员差异的摘要，使集合层面的知识能够改善具体研究资源的发现？

为检验这一思路，我们计划分别评价组织与摘要质量、资源检索效果，以及构建和使用成本。比较需要控制信息访问条件与模型投入，考察逐资源检索、简单聚类后摘要及相关 community 检索方法，区分资源组织与摘要各自带来的作用。最终需要回答的是：系统是否帮助 Agent 找到更符合需求的资源，这种收益来自哪些设计，以及收益是否足以支持构建集合知识的投入。
